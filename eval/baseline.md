# 评测基线：结论、理由和适用边界

基线只证明**指定模型、指定代码、指定任务**当时的表现。跨模型、跨任务口径、跨 Git 提交的数字不能直接宣称是内核能力的提升。原始 JSON 保留在 `eval/baselines/`，本页只保留足以做决策的结论。

### 这个 19/20 该怎么读

失败点在检查器的**表格形状契约**上，不在「能不能写文档」上。三轮的报错都落在同一个分支：检查器按 `^\|\s*命令\s*\|\s*[^|]+\s*\|` 找表头、按两列正则抓数据行，而模型实际产出的是三列表格（脚本名 + 命令 + 说明）或把脚本名直接当命令列。用六种表格形态跑检查器可以复现两种报错（见 [最终报告](../docs/reviews/2026-11-20-eval-baseline.md) 第 3 节）：

- 三列、表头首列写 `npm script` → `正文表格必须有命令列和说明列`；
- 两列表头配三列数据行，或命令列只写脚本名（`test` 而不是 `npm run test`）→ `文档表格必须逐项列出 package.json 的全部 npm scripts`。

也就是说：**这 3 次失败是可预测的格式不符，不是能力抖动**；单独复跑通过，是那一次恰好写成了两列。检查器要不要放宽、任务描述要不要写死格式，属于需要单独决策的改动，本次未改。

### Token 成本的现状

单次请求的固定开销已经量过：系统提示 1,600 tokens（7,753 字符）+ 工具定义 1,972 tokens（9 个工具，线上 JSON 7,987 字符），合计 **3,572 tokens**，每次请求都要重发一遍。三轮平均每请求 prompt 4,010 tokens，即 **约 89% 的 prompt 是这段固定内容**；固定块占全部 Token 账单（1,630,613）的 87%。

Completion 只占 2.4%（38,825 / 1,630,613）。工具返回结果也不是大头：单任务实测 9 次工具调用的返回合计约 700 字符。

和 11 月 5 日 v2 基线（`eac798d`，1,328 tokens/请求）相比，单请求成本涨到 3.1 倍，其中 **96% 来自固定块变大**（892 → 3,572 tokens：系统提示 654 → 7,753 字符，工具从 7 个 2,679 字符涨到 9 个 7,977 字符）。另一部分是请求数从 89.5 涨到 132（+47%），但这部分受套件和任务变化影响，不能单独归因于内核。

**采用 v2 的理由**：提示词要求模型每次只运行一条简单 Shell 命令，以减少复杂拼接、管道和 Shell 语法失败导致的额外往返。在该样本上，请求中位数下降 11.8%，Token 中位数下降 14.5%，墙钟中位数下降 10.4%；Token 六轮极差由 1.42 倍收窄到 1.22 倍。该实验支持这一提示词在这些任务上的取舍，**不能证明对所有 Shell 工作负载都有收益**。

## 不能过度解释分数

- 2026-11-14 审查发现的 **5 个历史检查器漏检点**已纳入 `2026-11-19-checkers-v2` 加强范围；另补充了嵌套目录扫描、常量提取、共享校验和 guard clause 的结构检查。具体改动见 [评测集说明](./README.md)。`eval:check` 仍只证明初始状态会失败，检查器严格性由 `test/eval-task-checkers.test.mjs` 的正反例测试保护。
- **不同提交、不同套件、不同模型的成绩不能混算。** checkers-v2 三轮基线固定在同一提交 `76a024a`、同一模型 `hy3`、同一套件上；旧 v1/v2 数字只作历史对照。
- 三轮里 `04-create-doc` 的 3 次失败是**格式契约不符**，不是随机波动；它的单独复跑通过也不能反过来把成绩改成 20/20。真实分布就是 57/60。
- 所有结果都来自当时固定的 `hy3` 和评测任务；现行 `main` 已演进，不能继承旧版的 120/120 结论。
- `usage` 缺失不能填 0；请求次数、工具执行次数、Token 和墙钟是不同指标。诊断运行有 I/O 开销，不能和未开启追踪的时间直接比。
- 第一阶段单轮 DeepSeek-V4.1-Flash 的 20/20、178 请求、389,074 tokens、66.5 秒，仅作为历史样本，不用于和 `hy3` 比较内核强弱。
- 三轮覆盖的能力有限：没有触发上下文压缩，也没有启用子 Agent 工具，因此这两块的成本与收益**在本次基线里没有任何数据**。
