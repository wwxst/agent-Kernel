### 本轮发现并修正的评测缺陷

第一次跑多轮时，`20-fix-email-regex` 出现一次 `[check]` 失败：`user+tag@my-site.io 应该被接受`。检查器一直要求接受 `+tag`，但 `task.md` 只写了「带点的用户名」和「带连字符的域名」。有一轮 agent 严格照着 prompt 实现，就被检查器判错。

修复：在 `task.md` 里明确列出两种合法形状（`first.last@example.com`、`user+tag@my-site.io`）。修正后 3 轮都通过。这条不是 agent 的失败，是评测任务**描述与断言不一致**；多轮评测把它暴露了出来。

## 怎么复现

1. `.env` 里填 `BASE_URL`、`API_KEY`、`MODEL=hy3`（或任何 OpenAI 兼容端点）。
2. `npm run eval:check`：不需要 Key，确认 20 个任务的初始状态都会**断言失败**。
3. `npm run eval -- --jobs 4`：跑一轮；控制台打印表格，同时写 `eval/results/<时间戳>.json`。
4. 重复 3 次；`npm run eval:summary` 汇总最近几轮完整评测的中位数。

## 口径

- **一次请求** = 一次 `llm.chat()` 调用；**一次工具调用** = 真正执行的工具。被预算或取消拦下、只写了 `ERROR: not run` 的调用不计入。
- token 全部来自端点返回的 `usage`。三轮基线都没有缺失 usage，所以合计是精确值；如果有缺失，汇总会写 `at least` 并单列未知数量。
- 墙钟是 4 并发下的实际耗时；「任务耗时合计」是每个任务耗时相加，两者不能直接比较。
- 通过率是 3/3 轮都 20/20，但这仍是**同一台机器、同一个模型、同一天**的样本。要判断长期稳定性，需要跨天、跨模型、更多轮次的数据。
