## 1. 症状

六轮全量评测里，13、20、08 的 token 波动分别是 5.27×、5.05×、3.87×。这不是检查器问题：所有轮次、所有路径最终都通过；波动来自模型自己多走了几轮。

## 3. 请求级 Token 增长

每次请求都会重发完整 transcript，所以 prompt tokens 随请求数近似线性增长：

| 任务 | 请求均值 | prompt 首→末（均值） | 每多一轮约增加 | 最大消息字符 | shell 调用 | shell 失败 | 编辑次数 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 13-callback-to-promise | 11.8 | 1,003 → 2,671 | +1,668 / 16 步 ≈ 104 | 6,746 | 9.0 | 5.2 | 2.0 |
| 20-fix-email-regex | 8.8 | 1,032 → 2,077 | +1,045 / 8 步 ≈ 131 | 6,124 | 3.6 | 2.2 | 2.2 |
| 08-extract-duplication | 5.2 | 1,004 → 1,546 | +542 / 4 步 ≈ 135 | 2,496 | 0.8 | 0.6 | 1.0 |

以 13 号最长的一轮为例（17 请求 / 35,544 tokens）：prompt 从 1,003 涨到 2,708，单轮 completion 只有 20–175。**成本主要不是模型输出，也不是工具结果大小**（shell 结果大多只有 7–810 字符），而是「多一次请求 = 重发一次更长的历史」。

推论：降低成本的杠杆是**减少请求数**，不是先做上下文压缩。压缩只能降低每次请求的 prompt，但高方差任务的请求数本身就会翻几倍。

## 4. 三个案例

### 4.1 13 号：验证路径 + shell 语法重试

最长一轮（17 请求）的工具序列：

1. `ls` → `glob` → 读 `app.mjs` / `config.mjs`；
2. 写 `config.mjs`（211→149 字节）、写 `app.mjs`（224→206）；
3. `node app.mjs; echo "exit code: $?"` → **exit 1**（此时 `config.json` 还不存在，失败是任务要求的行为）；
4. 用多行/`;` 的写法创建 `config.json` 并运行 → exit 0；
5. 之后又用 `&&`、`|`、`node -e` 等不同写法重复跑了 **7 次**，其中 3 次因 `|` 被当成命令分隔符/引号问题失败；
6. 最后读 `out.log`、删除临时文件。

关键观察：

- 一部分失败是**合法验证**（缺 `config.json` 时应当 exit 1）；
- 另一部分是**shell 语法失败**（把 `|` 当分隔符、多行命令、引号变体）；
- 每次失败都要多一轮模型请求来纠正，prompt 又随历史变长。

### 4.2 20 号：临时测试文件反复写 / 跑 / 删

某轮（10 请求 / 20,096 tokens）的工具序列：

1. `grep` + 读 `validate.mjs`；
2. `edit` 修正则（101→114 字节）；
3. 用 `node --input-type=module -e '...'` 做内联验证 → exit 1；
4. 写 `test_email.mjs`（535 字节）并跑 → exit 0；
5. **又重写** `test_email.mjs`（535→642 字节）并跑 → exit 1；
6. `del test_email.mjs` → exit 0。

同一件事被验证了三次，其中两次是临时测试文件；第二次重写后反而失败，最后删掉。任务本身只要求改 `validate.mjs`。

### 4.3 08 号：离群点来自平台不匹配 + 临时文件

第 4 轮（10 请求 / 17,497 tokens）在正确写完 `validate.mjs` 后：

1. 内联 `node --input-type=module -e '...'` 验证 → exit 1；
2. 尝试写 **`/tmp/test_validate.mjs`** → `ERROR: path escapes workspace`（路径守卫正确拒绝）；
3. 改写工作区内的 `test_validate.mjs`；
4. `node test_validate.mjs && rm test_validate.mjs` → exit 1（Windows 上没有 `rm`）；
5. `rm -f test_validate.mjs; ls` → exit 1；
6. 最后用 `del test_validate.mjs` → exit 0。

这是 **POSIX 命令用在 Windows shell** 上的典型绕路：`rm` 不存在，模型试了两次才换成 `del`；同时 `&&` 把「测试成功」和「删除」绑在一起，删除失败让整条命令看起来失败。

## 5. 根因排序

1. **Shell / 平台不匹配**：`|` 当分隔符、`rm` 用在 Windows、`/tmp` 绝对路径。直接造成 08 离群点和 13 的多次失败重试。
2. **临时测试文件 churn**：20 和 08 都出现写测试文件、重写、删除；任务并不要求这些文件。
3. **验证冗余**：13/20 在已经成功之后继续用不同写法验证同一行为。
4. **合法多路径验证**：13 的「缺 config 应 exit 1」是任务要求，这部分不算浪费；优化时必须保留。
5. **不是工具结果大小，也不是模型输出**：工具结果普遍很小，completion 占比低；成本由请求次数和重发历史主导。

## 6. 候选提示词 A：验证成功后不再重跑（未采纳）

在默认提示词后追加一行：

> Once a verification command succeeds, do not run it again; finish the task instead of adding more checks.

3 轮结果（13/20/08，全部通过）：21 请求 / 33,347 tokens；22 / 35,853；28 / 54,071。均值 23.7 请求 / 41,090 tokens，对比 3 轮基线 24.3 / 43,129 —— 只有约 -3% / -5%，最坏一轮反而略高。

**结论：不采纳。** 根因不是「重复成功的命令」，而是命令本身失败后的语法重试；这条提示词打偏了。

## 8. 为什么没有直接应用

候选 B 的证据不错，但本阶段**刻意不把提示词改到 `src/`**：

- 跨天实验固定在同一 commit / tag `stability-2026-11-04` 上；中途换提示词会让未来三天的数据与现有 6 轮不可比；
- 3 个任务的 A/B 只有 5 轮，完整 20 任务只有 1 轮；先把跨天基线跑完，再应用并重新建立同日基线，是更干净的单变量顺序；
- 这条提示词是 shell 专用的，值得先补一个更根本的候选 C（见下）再决定最终文本。

建议的应用顺序（下一阶段）：

1. 应用候选 B（一行系统提示词）；
2. 打新 tag `stability-2026-11-04-prompt-v2`；
3. 在新 tag 上重跑 6 轮同日基线；
4. 再开始跨天三天，全部用新 tag；旧 tag 的数据保留为历史。

## 9. 下一个候选（C）：平台感知的 shell 描述

08 的离群点根因是模型不知道 Windows shell 没有 `rm`。更根本的修法是在 `shell` 工具的 description 里写明平台：

> Run one shell command in the workspace root; uses cmd.exe on Windows and /bin/sh elsewhere; returns exit code plus stdout/stderr.

这是一条**工具描述**改动，比系统提示词更贴近使用现场；应先做 5 轮 A/B（尤其针对 08 和 13），确认能减少 `rm` / `|` 类失败，再考虑应用。它与候选 B 是两个变量，不能一起上。

## 10. 限制

- 5 轮/臂、单模型、单机、同一天；候选 B 的收益可能随日期/负载变化。
- 高方差任务在少量轮次里仍可能出现新的离群点；08 的 10 请求样本只出现过一次。
- diagnostics 记录的是 usage 与字符数，不是 tokenizer 级别；prompt token 仍以端点 usage 为准。
- 没有自动重试；空答复、限流、失败命令都按原样记录。
- 本阶段没有改任何评测任务或检查器。
