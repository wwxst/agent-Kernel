## 1. CLI 失败路径的 usage 输出

**问题**：CLI 只在 `agent.run()` 成功后打印 `[usage]`；失败（步数上限、token 预算、取消、模型错误）时只有 stderr 的一行错误，用户看不到这次失败花了多少 token。

**修改**（`src/cli.ts`）：

- `runTask` 用 try/catch 包住 `agent.run()`，两个分支都调用 `printUsage(agent.stats, …)`；
- 失败分支在错误文案前打印，并追加 `· task failed`；
- `printUsage` 继续遵守原来的口径：usage 缺失写 `at least`，软预算超限写 `budget exceeded (limit=…)`。

失败时现在长这样：

```
[usage] requests=2 tool_calls=1 tokens=220 (prompt=200 completion=20) · task failed
[agent] fatal: step limit 2 reached after executing 1 tool call(s); ...
```

**测试**（`test/cli.test.mjs`）：

- 步数上限失败：`requests=2 tool_calls=1 tokens=220` + `task failed`，退出码 1；
- token 预算失败：`requests=1 tool_calls=0 tokens=110` + `budget exceeded (limit=100) · task failed`；
- mock 端点支持可选 `usage`，让失败路径的账可精确断言。

这是一次独立的小修复：没有动 Agent Loop、预算语义或评测逻辑。

## 3. 唯一失败：第 4 轮 `10-delete-dead-code`

- 结果：`[task] model returned an empty final answer`
- 消耗：8 次请求、11 次工具调用、10,568 tokens、16.1s
- 行为：内核识别出「没有工具调用但 content 为空」，直接判失败，没有把空答复伪装成成功；usage 照常记录（CLI 失败路径修复后，这类失败现在也能看到账单）。
- 后续：第 5、6 轮该任务分别 5 请求 / 6,633 tokens 和 9 请求 / 12,645 tokens，均通过。**不是反复失败，是一次模型侧的空答复。**

这次失败恰好验证了两件事：稳定性不是 100%；内核在「模型答了个空」时选择失败而不是静默成功。

观察：

- 三个任务都出现了「一次做对」和「反复读改」两种路径，而且**两种都通过了检查**。波动来自模型自己的路径选择，不是评测判定。

- 另一个新出现的离群点是 `08-extract-duplication` 第 6 轮的 11 请求 / 19,561 tokens（此前都是 4 请求 / 约 5,100），波动 3.87×。
- `07-add-quiet-flag` 也有一轮 11 请求 / 16,167 tokens，波动 2.70×。
- 其余任务大多稳定在 1.0–1.5×。完整逐任务表在 `eval/baseline.md`。

结论：**任务级方差是当前成本预测的主要误差来源**，不是内核开销，也不是任务规模。要稳定成本，应该减少模型绕路，而不是先做上下文压缩。

## 7. 跨天限制（必须说清楚）

这 6 轮全部发生在 **2026-11-04 当天**（本地时间 15:58–17:16，轮间相隔几分钟到约 70 分钟）。虽然时间上有间隔，但**不构成跨自然日验证**：

- 没有覆盖机器重启、隔夜缓存、模型服务版本变化、不同负载时段；
- 同一天内的模型行为可能高度相关，方差不代表跨天方差。

因此本轮能证明的是「同一天、同一模型、连续 6 轮能稳定完成 20 个真实任务」，不能证明跨天稳定性。要完成真正的跨天验证，需要在另一个自然日用同一命令再跑一轮（建议至少 3 天 × 每天 3 轮），并把 `eval/baselines/` 按日期归档。

## 10. 剩余风险

1. **跨天样本缺失**：当前结论只覆盖同一天；需要按日期归档后补跑。
2. **任务级方差大**：`13`、`20` 的 5 倍波动意味着单轮成本和耗时不可预测；中位数 + 余量才靠谱。
3. **空答复失败**：第 4 轮说明模型可能返回空最终答复；内核能识别，但任务会直接失败。是否要自动重试是产品决策，本阶段刻意不做。
4. **token 预算仍是软上限**：`tokenBudget.exceeded` 可见，但不会阻止最后一条回复顶穿。
5. **结果 Top N 确定性**：`glob` / `grep` 截断后仍受遍历顺序影响，已记录、未优化。
6. **Windows 真实 Ctrl-C**：仍无自动化端到端用例（Node 无法向子进程投递 SIGINT）。
7. **单模型样本**：`hy3` 的结论不能直接外推到其他模型。

## 11. 下一阶段建议（仍不扩大范围）

1. **完成跨天验证**：在另外 2–3 个自然日各跑 3 轮，按日期归档 `eval/baselines/`，比较每天的通过率、token 中位数与失败任务；这是当前最大的证据缺口。
2. **调查 13 / 20 / 08 的绕路原因**：用 `--keep` 保留高请求轮的工作区，看模型是重复读同一文件、反复改同一处，还是验证路径过长；优先改工具描述或提示词，不先做上下文压缩。
3. **测量请求级 prompt tokens**：记录每次请求的 prompt 大小与增长曲线，为「上下文是否真的是瓶颈」提供数据；仍不做自动压缩。
