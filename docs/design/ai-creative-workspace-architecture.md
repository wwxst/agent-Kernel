# AI 创作画布与视频编辑器协作架构（设计提案）

> 状态：架构方向提案（产品职责方向已对齐，接口和实现细节待后续设计）
> 日期：2026-11-25
> 目标仓库：wwxst/agent-Kernel
> 说明：本文描述目标产品架构，不代表当前 main 已经实现 AI 创作画布、视频编辑器或相关媒体工具。

## 1. 一句话结论

产品由三个职责清楚、可以协作的部分组成：

- **Agent 客户端：大脑。** 理解用户目标、制定计划、选择工具、协调创作画布和视频编辑器。
- **AI 创作画布：创作中心。** 负责图片生成、视频生成、图片修改、参考素材、分镜和生成结果管理。
- **视频编辑器：剪辑中心。** 负责专业时间线、素材编排、字幕、音频、特效、预览、渲染和导出。

三者共享项目、素材和任务信息，但不互相吞并职责。

最重要的边界：

1. AI 创作画布是独立工作区，**不放进视频编辑器里面**。
2. 视频编辑器是独立产品和独立代码仓库，不把时间线、渲染引擎搬进 Agent Kernel。
3. Agent 通过工具调用创作服务和编辑器命令；工具的实际执行代码放在对应领域服务中。
4. 只有一套主 Agent Loop。Rea-video、Capsule Cinema、OpenMontage 不分别变成三个智能体。
5. 先复用有价值的现成代码，不完整复制三个项目，也不重复实现已有的编辑、生成和渲染能力。

## 2. 当前仓库基线与本提案边界

当前 agent-Kernel 的定位是极简 Coding Agent 内核。根据当前 README 和 docs/architecture.md：

- Agent Loop 负责模型请求、工具调用和结果回填。
- ToolRegistry 是 Tool 注册、参数校验和执行的统一入口。
- Skill 采用按需读取方式：系统提示提供目录，模型需要时再读取 Skill 正文。
- CLI/TUI 负责组装和展示。
- 当前没有 MCP Runtime、Plugin Runtime 或 Workflow Runtime。

因此，本提案是放在 agent-Kernel 仓库中的**跨产品架构设计文档**，不是要求把画布、视频编辑器或 Python 媒体处理代码直接加入 Kernel。

当前 Kernel 应继续保持通用：

- Core 不认识 Rea-video、Capsule Cinema、OpenMontage 等具体项目。
- Core 不根据「视频」「图片」等业务类型增加分支。
- 媒体处理、模型生成、时间线编辑都不进入 Agent Loop。
- 领域能力通过宿主装配的 Tool 和领域适配器接入。
- 不因为本项目需要视频能力，就提前增加通用插件运行时、通用工作流引擎或第二套 Agent Loop。

相关现状以 [README.md](../../README.md)、[docs/architecture.md](../architecture.md)、[AGENTS.md](../../AGENTS.md) 为准。

## 3. 三个产品模块的职责

### 3.1 Agent 客户端：理解和调度

负责：

- 与用户对话，理解目标和约束。
- 制定多步骤计划，决定先分析、再生成还是直接编辑。
- 通过 ToolRegistry 调用领域工具。
- 按需读取 Skills，了解专业工作流程。
- 汇总分析结果、生成结果和编辑器状态。
- 在付费生成、覆盖素材、替换镜头等关键操作前请求用户确认。
- 展示任务状态，并把结果交还给用户。

不负责：

- 自己实现视频镜头检测、图片生成或视频编码。
- 自己维护另一套视频时间线。
- 直接修改视频编辑器内部项目文件。
- 为三个上游项目各建立一套独立 Agent。

### 3.2 AI 创作画布：创作图片和视频素材

画布是与视频编辑器并列的独立工作区，不是视频编辑器里的一个侧边栏，也不要求第一版就做成单独的桌面应用进程。它的具体 UI 宿主和进程边界在客户端实现设计中确定。

第一版优先做成「生成工作台 + 分镜卡片 + 素材管理」，而不是一开始就做复杂的无限节点画布。

建议能力：

- 文生图、图生图、图片局部修改和扩图。
- 文生视频、图生视频、首尾帧生成及参考素材生成（以各模型实际能力为准）。
- 多模型选择和模型能力展示。
- 参考图片、参考视频和提示词管理。
- 多结果生成、并排比较、选中和版本管理。
- 生成任务进度、失败原因、取消和重试。
- 分镜卡片：每个镜头的画面描述、提示词、参考素材和生成结果。
- 将选中的生成结果保存为项目素材，供视频编辑器使用。

画布不负责：

- 专业多轨时间线。
- 最终成片的剪辑编排。
- 视频编辑器已有的字幕、音频、特效和渲染能力。

节点式工作流可以作为后续增强，不是第一版前置条件。

### 3.3 视频编辑器：专业剪辑和成片

视频编辑器保留独立代码仓库和自身媒体领域模型，负责：

- 项目、轨道、片段和时间线。
- 素材预览、剪切、移动、排序和替换。
- 字幕、音频、转场、特效和画面调整。
- 播放预览、渲染和导出。
- 编辑器自己的撤销、重做、保存和恢复机制。

Agent 可以通过编辑器公开的命令接口操作它，但不能绕过编辑器直接改内部时间线文件。

已确定的产品使用方式：

1. **独立模式：** 视频编辑器单独运行，并带有 Agent 助手面板。
2. **自有客户端嵌入模式：** 视频编辑器完整交互界面嵌入用户自己的 Agent 客户端。它仍然是独立编辑器进程，由宿主与编辑器之间的嵌入/控制通道协作。

第一阶段优先打通自有 Agent 客户端的完整嵌入。暂不以开发第三方视频编辑软件插件为目标。

## 4. 总体结构

~~~text
用户
 │
 ▼
Agent 客户端 / Host
 ├── Agent Kernel
 │    ├── 唯一主 Agent Loop
 │    ├── ToolRegistry
 │    └── 按需读取 Skills
 │
 ├── AI 创作画布工作区
 │    ├── 图片生成与修改
 │    ├── 视频生成
 │    ├── 分镜卡片
 │    └── 生成结果与素材选择
 │
 └── 视频编辑器 Host
      └── 嵌入独立运行的视频编辑器进程
             ├── 时间线
             ├── 预览
             └── 渲染与导出

Agent ToolRegistry
 │
 ├── 创作领域适配器
 │    ├── 图片/视频生成服务
 │    ├── 视频分析 Worker（复用 Rea-video）
 │    └── 视频配方/复刻 Worker（选择性复用 Capsule）
 │
 └── 编辑器控制适配器
      └── 视频编辑器公开命令接口

共享基础能力
 ├── Project：项目身份和元数据
 ├── Asset：素材索引和文件引用
 └── Job：生成/分析任务状态与结果
~~~

图中是逻辑关系，不要求所有模块运行在同一个进程。尤其是视频编辑器保持独立进程，媒体分析和生成也可以由独立 Worker 执行。

## 5. 工具、Skill 和智能体的分工

### 5.1 以 Tool 为主，不把三个仓库分别包装成 Agent

适合做成 Tool 的，是输入和输出明确、可以单独执行的动作：

| Tool 示例 | 作用 | 实际执行位置 |
| --- | --- | --- |
| analyze_reference_video | 分析参考视频并生成报告 | 视频分析 Worker |
| extract_video_shots | 提取镜头及时间信息 | 视频分析 Worker |
| generate_image | 生成图片 | 创作服务 |
| generate_video | 生成视频 | 创作服务 |
| get_generation_job | 查询生成任务 | 创作服务 |
| cancel_generation_job | 取消生成任务 | 创作服务 |
| create_remake_plan | 根据分析结果制定复刻方案 | 复刻/配方服务 |
| save_video_recipe | 保存可复用视频配方 | 配方服务 |
| regenerate_shot | 重新生成指定镜头 | 创作服务/配方服务 |
| editor_get_selection | 获取编辑器当前选区 | 编辑器控制接口 |
| editor_import_assets | 把素材导入编辑器项目 | 编辑器控制接口 |
| editor_insert_clip | 将素材放入指定时间线位置 | 编辑器控制接口 |
| editor_replace_clip | 替换指定时间线片段 | 编辑器控制接口 |
| editor_render | 请求编辑器渲染 | 编辑器控制接口 |

这张表是能力边界示例，不是要求一次性实现所有 Tool。最终工具数量应根据现有编辑器和创作服务的实际能力去重后确定。

### 5.2 Skill 只负责指导工作流程

Skill 是给 Agent 看的操作说明，不代替执行代码。

建议先保留少量高层 Skill：

- video-analysis：什么时候分析参考视频、如何理解报告。
- video-remake：如何从分析结果制定复刻方案。
- ai-media-creation：如何选择图片/视频模型、组织参考素材和生成任务。
- video-editing：如何安全地查询和修改编辑器项目。

不要把三个上游仓库的 Skills 原样全部复制进来。只保留与自有工具接口匹配、确实能提高执行质量的说明。

### 5.3 什么时候才需要专业 Agent

第一版不需要 Rea-video Agent、Capsule Agent、OpenMontage Agent 三套智能体。

复杂任务由唯一主 Agent Loop 规划，再调用多个 Tool。固定、可重复的步骤放在领域服务的确定性流程里执行，不让模型为每个小步骤反复思考。

只有当真实任务评测证明单个 Agent 的规划能力不足、且职责边界确实独立时，才考虑增加一个视频生产 Subagent；不预先建设多智能体团队或通用调度系统。

## 6. 三个上游项目怎么复用

### 6.1 Rea-video：视频逆向分析

仓库：[JuneYaooo/rea-video](https://github.com/JuneYaooo/rea-video)

它的核心价值是逐镜头分析参考视频，判断画面制作方式，并输出面向人的报告和面向 Agent 的 VIDEO.md。README 说明它提供 Python CLI，依赖 Python 3.10+ 和 FFmpeg，也可以作为 Agent 插件安装 Skill。

建议复用：

- 镜头拆解和时间信息。
- 关键帧与画面分析流程。
- 字幕、贴纸、转场、声音和剪辑节奏分析。
- 对实拍、AI 视频、3D/动画、代码模板和混合视频的分析方法。
- HTML/PDF 报告与 VIDEO.md 输出。

接入方式：

- 保留其 Python CLI/分析代码作为独立 Worker 或进程适配器。
- Agent 通过 analyze_reference_video 等 Tool 调用，不在 Kernel 内运行 Python 分析逻辑。
- 将分析结果转换为自有的 AnalysisReport / StoryboardShot 数据结构。
- 原始 VIDEO.md 和报告可以作为分析附件保存，但不要把 VIDEO.md 直接当成视频编辑器的内部时间线格式。

不重复做：

- 不让 Rea-video 负责最终剪辑和渲染。
- 不把它自己的 Skill、CLI 和 Agent 插件安装流程整体搬进 Kernel。

许可证：仓库当前 LICENSE 为 Apache-2.0。复用时仍需保留许可证和版权声明，并检查其依赖项许可证。

### 6.2 Capsule Cinema：视频复刻和配方

仓库：[JuneYaooo/capsule-cinema](https://github.com/JuneYaooo/capsule-cinema)

它的核心价值是把视频制作方法保存成可迁移的配方，支持先审分镜、选择生成渠道、单镜头返工、发布前 QA 和配方复用。其 README 明确说明它可以与 Rea-video 配合：先拆解参考视频，再根据拆解结果制作新版本。

建议复用：

- 配方的数据组织方式。
- 分镜审核和制作计划。
- 单镜头重新生成与局部返工。
- 发布前质量门和检查规则。
- 配方打包、迁移和跨主题复用。

接入方式：

- 把配方转换成自有的 Recipe / Storyboard 数据。
- 生成素材仍由 AI 创作画布管理。
- 镜头插入、替换、时间线修改和最终渲染交给自有视频编辑器。
- 配方保存可复用的结构、风格和制作规则，不保存当期密钥或不应复用的临时素材。

不重复做：

- 不采用它自己的最终视频拼接/渲染流程替代编辑器。
- 不把它的整套 Skill 安装系统变成 Kernel 的新运行时。

许可证：仓库当前 LICENSE 为 Apache-2.0。复用时保留许可证和版权声明，并检查依赖项。

### 6.3 OpenMontage：选择性借鉴 AI 视频生产能力

仓库：[OpenMontageInc/OpenMontage](https://github.com/OpenMontageInc/OpenMontage)

它是一个 Agentic 视频生产系统，包含 Pipeline、Stage Skill、工具注册/发现、模型 Provider、生产过程记录、质量检查，并使用 Remotion、HyperFrames 和 FFmpeg 等完成不同类型的视频合成。

建议借鉴：

- 生产 Pipeline 的阶段划分。
- Provider 能力描述和模型选择方法。
- 生成前的计划与用户确认。
- 生成后的多项质量检查。
- 任务过程可观察、可回放的思路。
- 有价值的模型 Provider 适配代码（通过代码审查后）。

不建议整体接入：

- 不复制它自己的 Agent 编排和工具注册体系。
- 不再引入第二套 Agent Loop。
- 不把它的 Backlot、Pipeline Runtime、Remotion/HyperFrames 渲染栈整体并入自有编辑器。
- 不让它和自有编辑器同时拥有最终时间线和渲染的控制权。

许可证：仓库当前 LICENSE 为 AGPL-3.0。**在确认商业分发、闭源边界和服务部署义务前，不复制、修改或随产品分发其代码。** 单纯把代码放进独立进程，并不能自动证明没有许可证义务。需要先做许可证审查，必要时获得授权或自行实现兼容接口。

## 7. 工具到底放在哪里

要区分「Agent 看到的 Tool 定义」和「Tool 实际执行代码」。

| 位置 | 放什么 | 不放什么 |
| --- | --- | --- |
| Agent 客户端/Kernel 装配层 | Tool 名称、描述、JSON Schema、调用路由、结果回传 | FFmpeg 处理逻辑、视频模型 SDK、时间线内部实现 |
| AI 创作服务 | 图片/视频模型适配、生成任务、生成结果、任务取消 | Agent Loop、专业剪辑时间线 |
| 视频分析 Worker | Rea-video 代码、镜头分析、报告生成 | 视频编辑器的最终时间线和渲染 |
| 视频配方/复刻服务 | Capsule 配方、分镜规划、局部返工逻辑 | 第二套 Agent Runtime、重复渲染器 |
| 视频编辑器 | 时间线命令、媒体处理、预览、渲染和导出 | Agent 的模型决策和通用 Skill 管理 |

原则：

- Agent 客户端负责决定何时调用哪个 Tool。
- 领域服务负责执行具体业务。
- UI 和 Agent 调用同一套领域服务，避免出现两套实现。
- 视频编辑器只通过公开命令接口接受操作，不让 Agent 直接写内部项目文件。
- 不要求每个 Tool 都是 MCP Server。优先使用适合本机产品的稳定 API/IPC；MCP 可以作为外围适配方式，但不因此给 Kernel 增加 MCP Runtime。

## 8. 项目、素材和任务数据边界

三个模块需要共享引用，但不应该强行共用所有内部数据结构。

建议先统一最少的跨模块对象：

| 对象 | 最少字段 | 所属职责 |
| --- | --- | --- |
| Project | project_id、名称、工作目录、版本 | 项目身份 |
| Asset | asset_id、project_id、类型、文件引用、来源、元数据 | 共享素材索引 |
| GenerationJob | job_id、project_id、任务类型、模型、状态、进度、输出 asset_id、错误 | 生成任务 |
| AnalysisReport | report_id、source_asset_id、镜头列表、字幕/音频分析、报告文件引用 | 视频分析 |
| StoryboardShot | shot_id、顺序、时长/时间范围、画面描述、提示词、参考 asset_id、生成结果 asset_id | 分镜与复刻 |

数据边界：

1. Asset 使用稳定 asset_id 在模块间引用，文件路径只是本机存储细节。
2. AI 生成的结果先成为项目素材，不自动等于时间线片段。
3. 用户或 Agent 选择素材后，再通过编辑器命令导入、插入或替换。
4. AnalysisReport 和 StoryboardShot 是分析/创作计划，不是编辑器内部时间线。
5. 视频编辑器自己的 Timeline、Track、Clip 和撤销/重做状态由编辑器拥有，不由 Kernel 或画布另建一份。
6. 分析时间信息应保留整数时间和源视频帧率/时间基信息；进入编辑器时由编辑器转换为自己的帧/时间基，避免浮点秒数导致切点漂移。
7. GenerationJob 和长时间分析任务由创作服务/Worker 管理状态、进度和取消。Kernel 不因此新增持久化 Task System。

## 9. 两条核心用户流程

### 9.1 从参考视频复刻

~~~text
用户给出参考视频
    ↓
Agent 规划分析任务
    ↓
调用 Rea-video Worker
    ↓
得到镜头、字幕、音频、节奏和制作方式分析
    ↓
转换为自有 AnalysisReport / StoryboardShot
    ↓
AI 创作画布展示分镜和参考素材
    ↓
用户确认复刻方案
    ↓
调用图片/视频生成服务，生成或替换指定镜头
    ↓
生成结果保存到项目 Asset
    ↓
用户选择素材，或授权 Agent 插入指定镜头
    ↓
视频编辑器导入素材并修改自己的时间线
    ↓
预览、质检、渲染和导出
~~~

### 9.2 从零制作视频

~~~text
用户描述视频目标
    ↓
Agent 生成脚本和分镜计划
    ↓
AI 创作画布展示分镜卡片
    ↓
按镜头生成图片/视频/配音等素材
    ↓
用户选择或要求局部返工
    ↓
素材进入项目 Asset
    ↓
视频编辑器组装时间线
    ↓
Agent 辅助字幕、音频、剪辑和检查
    ↓
编辑器完成最终渲染和导出
~~~

这两条流程共用 Project、Asset 和 Job，但不共用一套臃肿的业务运行时。

## 10. 进程、通信和长任务

建议保持清楚的进程边界：

- Agent Kernel 是决策与 Tool 调度内核。
- AI 创作服务/Worker 负责模型生成和媒体分析等耗时任务。
- 视频编辑器保持独立进程，提供可被宿主控制的编辑器接口。
- Agent 客户端作为 Host，负责工作区切换、任务展示和编辑器嵌入。

通信要求：

- 工具调用有明确的请求/响应结构和版本。
- 长任务返回 job_id，服务端提供状态、进度、结果、错误和取消能力。
- 任务进度可以推送给 UI；不要求 Agent 为了等待进度不断向模型请求。
- 取消必须传到实际 Worker/模型任务，不能只在 UI 上隐藏状态。
- 编辑器控制通道至少要覆盖项目打开、素材导入、选区读取、插入/替换片段、渲染请求和错误回传。
- 嵌入通道还需要处理窗口附着、尺寸、可见性、焦点、DPI 和进程存活等宿主协作问题；具体协议由视频编辑器仓库单独设计。

第一阶段不锁死 HTTP、JSON-RPC、命名管道或 MCP 的最终组合。先定义调用语义和数据契约，再按目标操作系统及嵌入方式选择传输。不要把传输协议选择变成重写 Agent Core 的理由。

## 11. 开发顺序：先打通一条纵向流程

这是个人开发项目，应该按一条可验收的端到端流程逐步推进，不同时启动多个大型子系统。

### 阶段 0：设计和许可审查

- 明确三个模块边界。
- 检查视频编辑器现有能力，列出重复项。
- 审查三个上游项目的源码、依赖、许可证和可复用范围。
- 定义最小 Project / Asset / Job / Storyboard 契约。

交付：设计确认和代码复用清单，不改 Agent Core 业务代码。

### 阶段 1：最小视频分析闭环

- 以独立 Worker 方式运行 Rea-video。
- 提供 analyze_reference_video Tool 适配器。
- 把结果转换成自有 AnalysisReport / StoryboardShot。
- 在 Agent 客户端中查看分析结果。

验收：输入一条本地视频，得到可读报告和结构化镜头数据；不需要先实现视频生成。

### 阶段 2：AI 创作画布 MVP

- 图片生成和结果对比。
- 视频生成和任务进度。
- 参考素材和提示词管理。
- 分镜卡片和单镜头重新生成。
- 生成结果保存到统一项目素材库。

验收：至少能为一个分镜生成图片/视频素材，并能查看、比较和重新生成。

### 阶段 3：编辑器联动闭环

- Agent 客户端能打开/聚焦自有视频编辑器。
- 画布生成素材能进入编辑器项目。
- Agent 能读取选区、插入或替换指定片段。
- 编辑器能返回操作结果和渲染状态。

验收：完成「参考视频分析 → 生成一个替换镜头 → 放入时间线 → 预览和导出」的端到端流程。

### 阶段 4：Capsule 配方能力

- 将成熟分镜和制作规则保存为配方。
- 支持换主题复用。
- 支持单镜头返工。
- 增加发布前质量门。

验收：同一个配方能用不同主题生成新项目，且局部返工不要求重做全部镜头。

### 阶段 5：选择性吸收 OpenMontage

仅在许可证审查通过后，评估 Provider 适配、生产阶段组织和质量检测代码。优先复用独立、边界清楚的能力，不整体合并其 Agent、Pipeline Runtime 和渲染体系。

## 12. 不做什么

为了避免重复和过度设计，第一阶段明确不做：

- 不把 AI 创作画布塞进视频编辑器。
- 不在 Agent Kernel 内实现视频分析、图片/视频生成、FFmpeg 或时间线。
- 不把三个上游项目各包装成一个智能体。
- 不把所有上游 Skills 原样搬进自有 Skill 目录。
- 不把 Rea-video 的报告格式当作自有编辑器的项目格式。
- 不让 Capsule 或 OpenMontage 拥有第二套最终时间线和渲染引擎。
- 不为了接入这些项目而增加第二套 Agent Loop、多智能体自主调度或通用 Workflow Runtime。
- 不在第一版实现复杂节点式无限画布。
- 不在第一阶段开发第三方视频编辑软件插件。
- 不在许可证审查前复制或分发 OpenMontage 的 AGPL 代码。

## 13. 主要风险和控制措施

| 风险 | 控制措施 |
| --- | --- |
| 上游项目功能与自有编辑器重复 | 先做能力盘点，只接入缺少且有价值的部分 |
| OpenMontage AGPL-3.0 | 先做许可证审查，不假设独立进程自动免责 |
| Python / FFmpeg 环境差异 | 独立 Worker，检查版本和依赖，明确错误 |
| 图片/视频模型参数差异 | 由 Provider 能力描述驱动 UI，不把参数写死 |
| 生成 API 费用 | 显示预计费用/计费信息；关键付费任务执行前确认 |
| 长任务卡住或无法取消 | Job 状态、进度、超时、取消和失败原因必须可观察 |
| 分析切点与编辑器帧率不一致 | 保留源时间基，由编辑器负责精确转换 |
| Agent 直接改坏时间线 | 只能通过编辑器公开命令操作，重要替换可撤销/需确认 |
| 素材重复或丢失 | 使用稳定 asset_id 和项目级素材索引 |
| Kernel 被领域逻辑污染 | 领域适配器放在宿主/服务层，Core 保持通用 |

## 14. 已对齐方向与待确认细节

### 已对齐的方向

- Agent 客户端、AI 创作画布、视频编辑器是三个职责不同的部分。
- AI 创作画布独立于视频编辑器，不作为编辑器的附属面板。
- Agent 是统一的大脑，负责规划和调用工具。
- 视频编辑器保留独立仓库和专业剪辑职责。
- 视频编辑器支持独立运行（带 Agent 面板）和嵌入自有 Agent 客户端两种产品模式。
- 工具优先，Skill 负责说明工作流程；不为三个上游项目各创建一个 Agent。
- 三个上游项目按能力选择性复用，不整仓搬运。
- Agent Kernel 保持一个主 Agent Loop，不增加视频专用分支或通用工作流运行时。

### 后续需要单独确认的细节

- AI 创作画布 UI 的具体宿主和进程边界。
- Agent 与创作服务、视频编辑器之间最终采用的 IPC/API 组合。
- Project / Asset / Job / Storyboard 的正式 Schema 和版本策略。
- 三个上游项目逐文件、逐依赖的代码复用清单。
- OpenMontage 的 AGPL-3.0 对目标分发方式的具体影响。
- 视频编辑器嵌入接口在 Windows、macOS、Linux 上的实现和降级策略。

这些细节不影响当前已经对齐的产品职责边界，也不应成为提前改造 Agent Core 的理由。
