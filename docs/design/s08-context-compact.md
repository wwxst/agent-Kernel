# agent-Kernel 第 8 课：Context Compact 设计方案

> 状态：设计方案已实施；当前行为以代码、测试和 ADR-0029 为准。  
> 日期：2026-11-18  
> 适用仓库：`wwxst/agent-Kernel`，以本次检查的 `main` 分支为依据。  
> 基本原则：保持核心循环简单，优先复用现有实现，不为未来需求提前建设复杂架构。

## 1. 一句话说明

上下文压缩就是给正在工作的 Agent 腾地方：把较早、重复、过大的内容缩短，把真正重要的目标、决定和进度留下，让 Agent 在有限的模型窗口中继续工作。

压缩不是删除聊天记录，也不是长期记忆系统。完整历史可以留在本地，而每次发送给模型的内容只保留当前工作需要的部分。

## 2. 课程依据与竞品参考

课程第 8 课给出了四步流程：`tool_result_budget` → `snip_compact` → `micro_compact` → `compact_history`。图片中的 50,000 字符、最近 3 条工具结果均为教学示例，不是生产参数。课程强调原文过大时可存到磁盘，留下摘要；截图没有展示具体保存与恢复实现。

结合前期竞品研究，选择以下设计思想，而不照搬项目结构：

| 参考产品 | 借鉴什么 |
| --- | --- |
| Pi | 简单的 Token 预算、近期历史保留、结构化摘要与溢出恢复 |
| DeepSeek Harness | 上下文测量、工具结果裁剪、历史总结各自负责明确的事情；原始历史与模型上下文分离 |
| Claude Code | 清理过时工具结果，自动压缩 |
| Codex | 压缩属于运行时维护；原生压缩可留作未来适配器能力 |
| OpenCode | 更新已有摘要，防止摘要无限膨胀；失败后有限恢复 |

本方案是针对当前仓库的工程设计，不代表课程源码或竞品的完整实现。

## 3. 实施前仓库情况（设计时基线）

当前 `src/core/agent.ts` 已实现字符预算和基础压缩：默认 120,000 字符；超过预算后尝试压至 85%；较早完整轮次会被转换成文字预览；历史工具结果会按需裁剪至 800 或 240 字符；优先保留最近 6 条已可裁剪的结果，当前批次在模型读取前受到保护。摘要追加进唯一的 system 消息，达到上限后从前面裁掉；其长度最多 12,000 字符。

`src/model/llm.ts` 已读取真实 `usage`，默认最大输出 8,192 Token，但当前已检查的模型接口没有提供上下文窗口容量或专门的溢出错误类型。`test/agent.test.mjs` 已有工具配对与最新批次保护测试。

需要特别注意两处集成约束：

- `src/core/tool-log.ts` 的可选日志会截短、脱敏内容，不能当作可恢复的完整原始历史。
- `src/cli.ts` 有按 `transcript.length` 记录本轮起点、再用 `slice()` 查找本轮回复的逻辑。压缩会改变数组长度，所以需要一并检查，不能让压缩导致 UI 丢失本轮真实结果。

当前最主要的不足：

| 问题 | 改进方向 |
| --- | --- |
| 只按字符数判断压力 | 引入模型窗口和 Token 估算 |
| 优先移除旧轮次，再裁剪工具结果 | 优先处理工具结果，再总结历史 |
| 摘要只是截取原文 | 使用模型生成可继续执行的结构化摘要 |
| 摘要不断追加，最后截头 | 每次更新为一份新的合并摘要 |
| 当前长任务的工具调用、参数和推理会持续积累 | 允许在完整工具批次边界压缩已完成步骤，而不限于已结束的用户轮次 |
| 压缩可能丢失原始内容 | 保存可恢复原文，模型上下文与历史记录分开 |
| 超限后没有明确恢复路径 | 识别真实上下文溢出，有限压缩重试 |

## 4. 目标与边界

### 4.1 本课必须解决

1. 自动判断是否需要压缩，减少不必要的模型调用。
2. 优先精简大体积工具结果，不破坏工具调用协议。
3. 对较早历史生成结构化摘要，让当前任务能正确继续。
4. 压缩失败时保留可恢复的状态，不能悄悄丢弃重要信息。
5. 对明确的上下文超限进行有限恢复，避免死循环。
6. 保持现有取消、预算、统计、工具执行与 UI 行为正确。

### 4.2 本课暂时不做

不做长期记忆提取、跨会话任务恢复、任务依赖图、后台预压缩、复杂事件总线、多模型调度、跨 Agent 上下文共享、向量数据库和 Codex 专属压缩协议。

第 9 课 Memory 解决跨会话记忆；第 10 课 Task System 解决任务落盘及依赖。第 8 课只做当前上下文管理。为压缩提供的本地原文存档，不等于完整的会话持久化或自动恢复系统。

## 5. 总体架构

逻辑职责分为四部分，不要求为每一部分建立独立类、接口或目录：

- Context Budget：判断当前请求需要多少空间。
- Tool Result Compact：根据压力精简工具结果。
- History Compact：总结较早历史和旧摘要。
- Compact Verify：检查新上下文，再决定是否替换。

Agent Loop 仍然负责调度、执行工具、请求模型及停止条件。压缩机制负责准备下一次模型请求使用的上下文，不负责执行业务工具，不引入第二套 Agent Loop。

```text
用户输入 / 上一批工具结果
           ↓
更新当前系统提示词，确定实际工具清单
           ↓
计算下一次请求的上下文压力
           ↓
空间足够 ───────────────────────────→ 调用模型
           ↓ 空间不足
工具结果预算 → Snip / Micro → 重新测量
           ↓ 仍不足
选择安全历史范围 → 生成并验证新摘要
           ↓
保存必要原文，提交压缩后的上下文
           ↓
重新测量 → 足够则调用模型；仍不足则有限恢复或明确报错
```

正常情况下，在每次真实业务模型请求前统一检查，而不是在 Run 开始、结束和工具批次结束各自重复执行压缩。摘要请求属于辅助请求，不递归触发自身的压缩流程。

## 6. 上下文预算：什么时候压缩

必须区分三种预算：

| 预算 | 作用 |
| --- | --- |
| 模型上下文窗口 | 一次请求能容纳多少输入和输出 |
| 最大输出 Token | 为模型生成答案、推理或工具参数预留的空间 |
| Run 累计 Token 预算 | 整个任务最多允许统计到多少消耗，与窗口容量不是一回事 |

测量实际将发送的请求，包括当前系统提示、项目指令、技能正文、用户消息、历史、摘要、工具调用参数与结果、工具定义，以及需要原样回传的推理字段。不能只统计消息正文。

建议以模型窗口大小、有效输出上限、安全余量决定触发线，初始使用约 80% 触发、约 70% 作为压缩目标，但必须确保输出预留和安全余量在窗口内。具体默认值由实测调整，不照搬竞品大窗口参数。

优先使用与当前模型、请求结构兼容的真实输入用量作为估算依据，并估算从上一次请求到现在的内容变化。缺少可靠依据时使用保守估算，特别注意中文、代码和 JSON 的 Token 密度。无法获得模型窗口大小时，继续使用当前字符预算作为兼容路径；明确标记是估算或字符数，不伪装成准确 Token 数。模型容量来自配置或可信适配器信息，不根据模型名字随意猜测。

压力低于触发线时不调用摘要模型；压缩后重新测量。设置触发线与目标线之间的差距，避免刚刚压缩完又立即压缩。

## 7. 工具结果压缩：先处理最占空间的内容

### 7.1 Tool Result Budget

同时考虑单条工具结果和所有工具结果的总占用。平时尽量保持原样；出现压力后，先处理最早、已被模型成功消费的结果。

最近 3 条已消费工具结果可作为初始保护数量，按实际调用批次与预算调整，并不是每次强制把剩余结果删掉。最新尚未被模型消费的整批结果优先保护，不受“最近 3 条”限制。只有收到有效模型响应，才认为该请求中的结果已被消费；请求失败不能算已阅读。

特别情况：如果最新工具结果本身太大，完整发送已无法进入窗口，不能沿用“永远完整发送”的规则硬发超限请求。必须先可靠保存完整结果，再向模型提供带来源、明确省略标记和可读取原文的方法的有限预览；必要时分段读取。如果无法保存或无法形成可用预览，应明确失败，而不是悄悄丢掉内容。这个行为需要更新原有测试，并继续保证普通情况下的完整结果保护。

### 7.2 Snip Compact

复用现有 `compactText()` 的头尾裁剪与字符边界处理：保留开头和结尾，中间显示省略标记。省略信息应包含真实原文来源或存档引用。原始工具调用 ID、名称、结果关系保持不变；不能把裁剪内容伪装成完整输出。

路径、错误、退出状态、关键行号和测试结果尽量保留，但头尾裁剪本身不能保证发现位于中间的所有关键信息，因此完整原文必须可恢复。

### 7.3 Micro Compact

只对明确可识别、不会改变含义的输出做细粒度精简，例如已知的重复进度日志。不要对任意代码、JSON、文件正文或错误堆栈泛化去重、折叠空白。没有可靠的处理规则时，就只使用 Snip；不为了满足课程名称强行增加危险逻辑。

裁剪和微压缩不消耗模型 Token。每次处理之后检查体积是否确实下降，已经达到目标就停止，不必进入历史摘要。

## 8. History Compact：让 Agent 不忘记任务

### 8.1 保留什么、压缩什么

- 当前系统规则与动态项目指令由原来源重新生成，不依赖摘要恢复。
- 当前用户明确提出的任务与关键约束应受到保护；保留最新原始消息和近期执行步骤。
- 较早的完整轮次以及长任务中已经结束、工具结果已配齐的步骤，可以选择为压缩范围。
- 不能切断 assistant 的 tool_calls 与对应 tool 消息，也不能压掉尚未处理完成的调用。
- 保留下来的模型消息及协议要求的字段原样保留，例如 DeepSeek 的 `reasoning_content`。不能为了节省 Token 擅自删除仍需按协议回传的字段。

历史范围选择应按 Token 预算和安全边界进行，不只是固定保留多少条聊天记录。长时间运行的单个用户任务也要能够压缩，否则即使工具结果被裁剪，调用参数和推理仍会累积。

### 8.2 摘要内容

第一版使用当前模型生成摘要，不增加独立摘要模型配置。摘要是一份工作交接记录，而非普通聊天概述。结构建议如下：

```text
## 用户目标
## 重要要求与限制
## 已确定的决定及原因
## 已完成工作及验证结果
## 当前工作与进度
## 关键文件、命令、错误及发现
## 未解决的问题和待办事项
## 下一步
```

保留准确的文件路径、分支、提交、接口名、命令、错误信息和测试状态。明确区分已执行、计划执行、失败和未验证；用户的新决定优先于旧决定。允许摘要省略能方便地从文件重新获取的细节。

### 8.3 更新摘要

第一次压缩：旧历史 → 新摘要。

再次压缩：上一次摘要 + 新的待压缩历史 → 一份更新后的摘要。

用新摘要替换旧摘要，不无限追加，不通过简单从头截字数清除旧摘要。保留尚未失效的要求，删除已经解决的待办。不要复制整份文件内容到摘要中。

### 8.4 摘要调用的安全边界

摘要调用只负责总结，不允许调用工具、写文件或继续业务任务。使用当前可用的模型能力，限制输出长度，区分辅助请求与业务请求；不把摘要阶段的流式文本展示成正常用户答复。摘要调用的费用、失败和取消都需要真实统计，并受现有 Run 预算约束。

传给摘要模型的历史和工具内容是待总结的数据，不是新的系统指令。摘要回填也不能提高历史内容的指令等级，禁止让工具输出或摘要覆盖真实系统规则。具体采用何种协议表示方式应服从当前模型接口，不能拼造不存在的工具调用或用户真实发言。

## 9. 原文保存和压缩后的上下文

明确两种数据用途：

- 原始记录：用户输入、真实工具结果、真实模型输出等，用于必要时回看和恢复。
- 活动上下文：当前要发给模型的系统提示、摘要、近期消息及必要工具结果。

不要求立即重构整个会话系统。优先实现最小的压缩前存档能力：只把将要省略的内容按会话隔离保存到宿主可管理的本地目录，并记录来源、完整性和可读取的引用。原文在首次裁剪前保存，后续裁剪不能用预览覆盖原文；无需要求用户重新执行可能产生副作用的工具来取回旧结果。

如存档失败，则不提交依赖该存档的有损压缩。保存位置、保留期限、清理方式和权限需要明确；原文可能包含密钥、源代码等敏感信息，不放进项目仓库、不自动上传、不混入普通日志。当前已截短的运行日志不能代替原文。

第一阶段可以先用已有的文件 IO 能力完成必要存档与读取，避免立即引入数据库、事件溯源、复杂会话索引或新的通用存储框架。后续第 9、10 课可以按真实需求扩展。

## 10. Verify：怎么保证压缩不把 Agent 搞坏

压缩应先准备候选上下文，检查通过后再整体替换当前活动上下文，不在生成摘要的过程中提前删除旧消息。

提交条件：

1. 摘要非空、符合最低结构要求，且模型没有报告输出截断或失败。
2. 新内容确实比被替换范围更短，并重新测量下一次完整请求的压力。
3. 当前任务、明确保护的用户原文和近期消息仍存在；保留的调用与结果完整配对、顺序正确。
4. 需要原文引用的内容已经成功保存，引用可用。
5. 取消未发生，被压缩的消息范围没有在处理过程中变化。

结构检查可以发现明显问题，但不能数学上保证模型摘要没有遗漏或编造。因此必须增加真实长任务质量测试、保留原文和关键状态保护，不能仅凭摘要格式正确就宣称语义无损。

摘要失败、取消、无有效缩减时保留当前上下文；如果已经完成了安全且可恢复的工具剪枝，可以保留该结果。必要时进行限定次数的恢复；无法安全继续则报错，并保留真实工作状态。

## 11. 上下文溢出后的恢复

模型若明确返回输入上下文超限，执行以下流程：

```text
识别上下文超限（不是普通网络错误，也不是输出长度截断）
    ↓
更强的安全压缩 → 检查请求是否确实缩小
    ↓
最多额外重新发送一次业务请求
    ↓
成功则继续；失败则明确停止并报告
```

不能重新执行上一批工具，不能把普通 HTTP 400、网络故障或输出上限错误都误判成上下文溢出。没有实际缩减或不可压缩部分本身就超限时，不再重试。强制恢复与通用网络重试分开计数，但都受现有取消和用量预算限制。

系统提示、工具定义或单条用户输入自身过大时，历史压缩可能无能为力；应该给出明确原因与可行的缩减建议，不静默改写用户原始要求。

## 12. 对当前内核的改造原则

以仓库实际结构为准，复用现有 `compactText()`、工具配对检查、模型客户端、取消处理、用量统计、错误机制和测试基础。

将上下文管理从 Agent 主循环的具体实现中收拢为简单、明确的职责边界。Agent 只负责在正确时机接入并控制请求准入；不为了追求模块数量设计插件系统或多层抽象。模型层负责提供模型窗口配置、有效输出限制及真实错误信息；存档通过宿主侧文件能力实现。现有完全访问权限模式不因此改变。

特别关注：

- 压缩不能破坏主 Agent 与 Subagent 的上下文隔离。共享实现可以复用，但每个 Agent 应有独立的上下文状态。
- 区分业务 Step 与辅助摘要请求；所有实际模型请求及费用如实记录，摘要不得绕过限制，也不能让统计重复或用户界面误报。
- 检查 CLI/TUI 对 transcript 数组索引的依赖，确保压缩前后本轮输出仍能准确展示，原有对外接口尽量兼容。
- 保持项目现有运行时零依赖原则，除非有充分理由并另行讨论。

不预设新增文件名称、类数量和固定接口。实施时应先检查最新 main、未合并分支及相关测试，再安排最小改动。

## 13. 实施步骤与阶段门槛

实施按“先摸清现状 → 先做好确定性压缩 → 再加入模型摘要 → 最后补齐恢复和长任务验收”的顺序推进。每个阶段都要有可运行的结果和测试，不要一次性大改 Agent Loop。

### 阶段 0：实施前检查（不改业务代码）

1. 同步并检查最新目标分支，确认实际基线、工作区状态和未合并改动。
2. 重新阅读 Agent Loop、模型请求与响应、Token 用量、工具结果生命周期、工具调用配对、CLI/TUI transcript、Subagent 和现有测试。
3. 运行相关现有测试，记录基线结果；确认当前字符压缩行为和已知限制。
4. 识别其他开发会话的未提交修改。不得 reset、覆盖、清理或顺手提交他人的工作；必要时使用独立分支或隔离工作区。

**阶段交付：** 一份简短的实施前检查记录，列出实际代码入口、可复用逻辑、需要修改的范围、测试基线和潜在冲突。

**进入下一阶段的条件：** 已确认改动范围，不需要先重写会话系统、模型层或 Agent Loop。如果发现设计与最新代码有重大冲突，先说明差异和最小调整方案，不盲目照文档硬做。

### 阶段 1：上下文预算与确定性工具结果压缩

按以下顺序实施：

1. 为模型提供可信的上下文窗口配置和有效输出上限；不根据模型名称猜容量。
2. 在每次业务模型请求发出前，基于实际请求内容检查预算，覆盖系统提示、动态指令、工具定义、历史消息、工具结果和协议要求保留的字段。
3. 优先使用可获得的真实 Token 用量校准估算；缺少可靠 Tokenizer 或模型窗口信息时，保留字符预算兼容路径，并明确它只是估算。
4. 加入工具结果单条与总量预算。先处理较早且已经被成功模型请求消费的结果；普通情况下保护最新完整工具结果批次。
5. 对必须裁剪的原文，先保存完整内容，再使用 Snip；Micro 只处理明确安全的重复日志等内容。
6. 每次裁剪后重新测量，达到目标就停止，不调用摘要模型做多余工作。
7. 保证工具调用 ID、工具名、结果配对和顺序不变；最新单条结果本身大到无法发送时，走“先存档、再提供有限预览/读取引用”的例外路径。

**阶段交付：**
- 可运行的模型上下文预算检查。
- 工具结果总量控制和安全裁剪。
- 最小可恢复的原文存档与引用。
- 对预算、最新结果保护、工具配对、超大单条结果、存档失败的自动化测试。

**本阶段不交付：** 模型生成的历史摘要、后台预压缩、跨会话记忆。

**通过条件：** 短对话不触发压缩；大量旧工具输出能优先被缩减；普通情况下最新批次不会被提前裁剪；任何有损裁剪都能追溯原文或明确失败；工具协议保持有效。

### 阶段 2：历史摘要与原子替换

1. 只选择完整、安全的历史范围：按完整轮次或已结束的工具调用批次切分，不切断未完成调用。
2. 将旧摘要与本次待压缩历史一起交给当前模型，生成一份新的结构化交接摘要。
3. 摘要必须覆盖用户目标、重要要求、已确定决策、已完成工作、验证结果、当前进度、关键文件/错误、未解决事项和下一步。
4. 摘要请求关闭工具调用能力，不递归触发自身压缩；摘要消耗、失败和取消纳入现有 Run 预算与统计。
5. 先生成候选上下文，再检查摘要有效性、消息配对、保留范围、原文引用和实际 Token 压力；检查通过后一次性替换活动上下文。
6. 新摘要替换旧摘要，不无限追加；失败、取消、输出截断或没有实际缩减时，保留原上下文。
7. 支持单个用户任务持续多轮工具调用时，在完整工具批次边界压缩已完成步骤，不局限于已经结束的用户轮次。

**阶段交付：**
- 结构化摘要生成与更新。
- 安全的历史范围选择和候选上下文验证。
- 摘要失败/取消/无效时的回退。
- 多轮压缩、长单轮任务、摘要费用与预算统计测试。

**通过条件：** 压缩后 Agent 能准确说清任务目标、约束、决策、已完成和未完成事项；工具调用配对正确；多次压缩不会让摘要无限增长；摘要失败不会破坏原上下文。

### 阶段 3：上下文溢出恢复、集成回归与最终验收

1. 只识别模型明确返回的上下文窗口超限错误；区分网络错误、普通 HTTP 错误和输出长度截断。
2. 首次请求明确超限后，执行一次更强的安全压缩；确认请求确实缩小后，最多额外发送一次业务请求。
3. 恢复时不得重新执行已经完成的工具调用；不可压缩内容本身超限时，停止并给出具体原因。
4. 检查取消、Run 预算、模型费用、错误传播和统计，摘要请求及失败请求不能漏计或重复计数。
5. 检查 CLI/TUI 对 transcript 索引的依赖，确认压缩不丢失本轮真实输出；检查 Subagent 与主 Agent 的上下文状态互相隔离。
6. 运行全量类型检查、测试和适用的长任务回放；记录未运行的检查和未覆盖风险。

**阶段交付：**
- 明确上下文溢出分类与最多一次额外恢复。
- CLI/TUI、Subagent、取消、预算和统计回归结果。
- 完整测试结果及最终实施报告。

**通过条件：** 只有明确上下文超限才触发恢复；最多额外重试一次；不重复执行工具；长任务经过多次压缩仍能完成；现有交互和权限行为不回退。

### 阶段执行规则

- 阶段 0 的检查完成后再动代码；阶段 1 通过后再加入模型摘要；阶段 2 通过后再做溢出恢复和最终集成。
- 每阶段只提交该阶段必需的代码和测试，避免把无关重构混进来。
- 如果某项能力在当前架构中无法安全实现，先交付安全降级路径并说明，不得用静默丢数据的方式“完成”功能。
- 不以新增文件数量、抽象层数量或代码行数作为交付目标；实现位置和接口由当前代码决定。

## 14. 交付边界与完成定义

### 14.1 本课必须交付

| 交付项 | 必须达到的结果 |
| --- | --- |
| 请求预算 | 每次业务模型请求前检查上下文；区分窗口、输出预留和 Run 累计预算 |
| 工具结果管理 | 单条和总量预算；旧结果优先；最新批次保护；安全 Snip / 必要 Micro |
| 原文可恢复 | 有损裁剪前保存完整原文；引用能定位并读取；存档失败不做依赖它的有损替换 |
| 历史摘要 | 结构化摘要；旧摘要与新历史合并更新；只压缩安全边界内的历史 |
| 原子验证 | 候选上下文检查通过后才替换；失败或取消保留旧上下文 |
| 溢出恢复 | 识别真实上下文超限；更强压缩后最多额外重试一次；不重跑工具 |
| 运行兼容 | 主 Agent、Subagent、CLI/TUI、取消、Run 预算和用量统计不回退 |
| 自动化验证 | 覆盖正常、超大输出、工具配对、多次压缩、失败、取消、溢出和长任务 |

### 14.2 明确不属于本课交付

以下内容不能因为实现 Context Compact 而顺手扩展：

- 第 9 课 Memory：跨会话记忆提取、长期偏好、知识库和向量检索。
- 第 10 课 Task System：任务持久化、任务依赖图、跨进程恢复和任务调度。
- 完整会话数据库、事件溯源、通用归档平台和自动清理服务。
- 后台并发预压缩、复杂调度器、多模型摘要路由。
- Codex 专属原生压缩协议、跨模型加密上下文传递。
- 多 Agent 共享上下文、Subagent 编排体系重构。
- 新的权限/审批机制、工具执行语义重构、Shell 或文件工具重做。
- 为压缩新增 UI 面板、命令体系或大规模 TUI 重构；本课只要求现有交互兼容。
- 向量数据库、Embedding、长期知识沉淀，以及对任意代码/JSON/日志进行不安全的语义改写。

### 14.3 改动范围与工程约束

1. 只修改实现本课能力直接需要的代码、测试和必要文档；优先复用当前实现。
2. 不预先规定文件名、类名或接口层级；不得为了“四个模块”强制拆成四套类或插件。
3. 不改变现有 Full Access 权限决策，不引入审批流程，不改变工具本身的执行语义。
4. 不新增运行时依赖。若确实需要 Tokenizer、持久化组件或其他依赖，先说明现有能力为什么不够及替代方案，不擅自扩大依赖面。
5. 不重写 Agent Loop、模型客户端、Session 或 CLI/TUI；只有存在明确缺陷且本课无法安全完成时，才提出最小必要调整。
6. 不覆盖其他开发会话的未提交修改；不 reset、强制 checkout、清理或提交无关文件。发现并发冲突时隔离工作并报告。
7. 实施完成后可以整理本地提交，但未经用户明确授权，不推送、不创建/更新发布版本、不合并主分支。

### 14.4 最终交付物

完成实施时，必须提供：

- **实现结果：** 修改了哪些文件，各自解决什么问题。
- **关键行为：** 压缩触发条件、工具结果保护规则、摘要策略、原文恢复方式、溢出重试规则。
- **测试记录：** 实际运行的命令、通过/失败数量、失败原因；没有运行的测试明确列出。
- **长任务验证：** 至少一个包含多轮工具调用和多次压缩的确定性回放，说明压缩前后任务状态是否保持。
- **风险与遗留：** 当前 Token 估算限制、存档清理/隐私边界、未覆盖模型差异和后续建议。
- **Git 状态：** 分支、提交 SHA、工作区状态，以及是否存在未提交的其他开发改动。

### 14.5 最终完成定义（Definition of Done）

只有同时满足以下条件，才可以报告“第 8 课 Context Compact 已完成”：

1. 预算判断覆盖完整模型请求，窗口、输出预留和 Run 预算没有混淆。
2. 普通短对话不会额外调用摘要模型。
3. 旧工具结果能优先缩减，最新批次和工具调用协议得到保护。
4. 所有有损裁剪都可追溯到完整原文，或明确失败而不静默丢失。
5. 历史摘要能多次更新，关键任务状态保留，失败时原上下文不被破坏。
6. 上下文溢出最多触发一次额外业务请求，不重复执行工具。
7. 主 Agent、Subagent、CLI/TUI、取消和 Token/费用统计通过回归。
8. 相关自动化测试和项目全量检查通过；未通过项和未验证项已明确列出。
9. 没有混入 Memory、Task System、权限重构或其他无关开发。

若某项因当前模型供应商不提供上下文窗口数据、无法可靠分类溢出错误等外部限制而不能完全满足，必须明确标记为“受限/未完成”，给出可验证的降级行为，不得把它包装成已完成。

## 15. 测试与验收标准

| 测试场景 | 预期结果 |
| --- | --- |
| 普通短对话 | 不发生摘要调用，正常执行 |
| 大量旧工具输出 | 优先裁剪，能节约空间则不调用摘要模型 |
| 一批工具返回 7 条结果 | 正常窗口内全部先交给模型，不被保留数量误删 |
| 单条或整批最新工具结果超大 | 安全存档并提供可读取的预览，或明确失败 |
| 旧历史超过预算 | 生成有效摘要，近期消息保留，调用配对正确 |
| 单轮任务执行很多步骤 | 已完成步骤可压缩，当前目标不丢失 |
| 多次压缩 | 旧摘要被更新而非不断追加，旧约束在仍有效时保留 |
| 摘要超长、为空、失败或内容不合格 | 不提交无效摘要，原历史可恢复 |
| 压缩中取消 | 不提交未完成摘要，不继续发新的请求 |
| 存档失败 | 不进行依赖存档的有损替换 |
| 模型返回上下文超限 | 确认实际缩减后最多额外重试一次，不重跑工具 |
| 中文、代码、长工具 Schema | 预算估算覆盖完整请求，不能把字符数当作精确 Token |
| DeepSeek 思考模式 | 保留的工具调用及其相关字段满足模型协议 |
| 子 Agent 压缩 | 不污染主 Agent 的上下文 |
| CLI/TUI 展示 | 不丢掉本轮完成结果，不伪造工具执行状态 |
| Run 预算与模型费用 | 摘要、失败请求和重试真实计数；未知用量不能补零 |

除了单元测试，还应使用模拟模型做确定性回放测试，并用真实长任务做质量对照：比较压缩前后任务完成率、重要要求遵守情况、重复读取及重复执行次数、上下文压力、辅助摘要费用和总体耗时。节省 Token 不能以明显降低任务完成质量为代价。

执行仓库已有的类型检查、全量测试与适用的评测。最终报告实际运行的命令、测试结果、改动和未验证事项，不宣称未运行的测试通过。

## 16. 最终设计结论

采用“先测量，后裁剪，必要时总结，验证后替换”的方案。保持一个 Agent Loop，不建设第二套调度系统；向 Pi 学习简洁，向 DeepSeek Harness 学习职责分离，向 Claude Code、OpenCode 和 Codex 学习长任务上下文维护。

最重要的不是压缩了多少文字，而是压缩后 Agent 还能准确继续工作。普通情况尽量不增加额外模型请求，超限时安全恢复；原文可追溯，摘要可更新，失败有明确边界。

本稿记录实施前的目标、规则、约束与验收标准。第 8 课已按本方案完成实施；当前行为以仓库代码、测试和 [ADR-0029](../adr/0029-context-compaction-is-bounded-and-recoverable.md) 为准。设计阶段的基线分析作为历史背景保留。
