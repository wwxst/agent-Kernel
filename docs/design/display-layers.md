# 展示分层：概览层与详情层

这份文档回答一个问题：**界面上的信息该怎么分层？** 终端和未来的 Web/桌面前端共用同一套答案，只是呈现手段不同。

## 核心原则

**主视图只回答「发生了什么」，不回答「具体是什么」。**

- 概览层：这一轮做了什么、成没成、花了多久。一眼扫完，不展开。
- 详情层：原始参数、完整输出、Diff、命令原文。需要时再看，默认不占地方。

这条原则和屏幕大小无关。终端窗口小、Web 窗口大，但**默认展开所有细节都会让人失去焦点**。

## 终端的三条硬约束

| 约束 | 后果 |
| --- | --- |
| 没有鼠标（为了保住原生滚轮/选中，不捕获鼠标） | 展开只能靠快捷键，而快捷键要靠箭头提示，提示一多就成噪音 |
| 只能追加（scrollback 不可回改） | 已打印的内容无法原地展开/折叠，展开历史必须换视图 |
| 窄、无重排 | 每层缩进都在吃宽度，超过两层就分不清层级 |

结论：**终端主视图最多两层，且不提供交互式展开。**

## 分层映射

| 层 | 终端（当前实现） | 未来前端 |
| --- | --- | --- |
| 概览 | 用户消息 + 事件行（`↳ 已读取 2 个文件 · 运行 1 条命令`）+ 回复 + 结果行 | 同样的三块，卡片式排列 |
| 详情 | `Ctrl+T` 的 transcript 全屏视图（可整屏重绘，能展开任意轮次） | 点击事件行 → 侧栏/抽屉/内联展开；或独立的会话详情页 |
| 全局 | 状态行（权限、请求数、token） | 顶部/底部状态栏 |

**关键**：详情层是**另一个视图**，不是主视图的一个折叠区域。终端受限于追加模型必须这样；前端即使能做到内联展开，也建议保持「主视图克制、详情另开」，否则长会话会变成一堵墙。

## 前端可以多做什么

终端做不到、前端可以做的：

- 真正的树形展开（点击、hover、键盘可达）
- 折叠状态持久化（刷新后记得哪些是展开的）
- 虚拟滚动（几千条事件不卡）
- 语法高亮、Diff 并排、图片预览
- 搜索并跳转到某次工具调用

但**不要**因此默认展开所有细节。默认视图的信息密度是产品决策，不是技术能力问题。

## 判断标准

一条信息该进概览层还是详情层？

- 用户扫一眼需要知道吗？→ 概览
- 只在排查/复盘时需要吗？→ 详情
- 是安全相关信息（哪条命令失败、为什么失败）吗？→ **必须进概览**，不许藏进详情
