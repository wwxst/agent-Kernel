# 外部 Agent 驱动客户端：让 AI 像个人开发者一样工作

> **文档定位：长期产品与架构方向。**
> 本文记录目标形态和设计边界，不代表当前代码已经实现这些能力，也不直接改变当前 Agent Loop、Full Access 或模块依赖规则。具体接口和实施方案仍需在功能开发前单独设计、评审。

## 1. 核心目标

我们要做的不只是一个能聊天、能调用工具的 Agent 客户端，而是一个**可以被其他 Agent 客户端连接和操控的通用工作环境**。

用户提出一个目标，例如“帮我开发一款视频编辑器”。外部的强模型 Agent 负责理解目标、做技术决策、安排工作和检查结果；我们的客户端提供项目工作区、文件、终端、浏览器、Git、执行模型和其他专业工具；廉价执行模型与确定性工具负责完成具体工作。

一句话概括：

**外部强模型负责指挥，我们的客户端负责组织和执行，廉价模型与专业工具负责干活，用户负责目标、监督和最终验收。**

## 2. 这里说的“外部 Agent 控制客户端”是什么意思？

目标流程是：

~~~text
用户提出目标
    ↓
外部中央 Agent（例如 Claude Code、Codex 等）
    │  理解需求、制定方案、拆分任务、检查结果
    ↓
外部控制接口
    │  连接、选择项目、派发任务、读取状态、接收事件
    ↓
我们的 Agent 客户端
    │  管理工作区、执行任务、调用模型和工具、展示过程
    ↓
本地执行模型 + 专业工具
    │  写代码、改文件、运行命令、编译、测试
    ↓
执行结果和事件返回外部中央 Agent
    │
    └──── 检查、纠正、继续派发，直到达到验收标准
~~~

这里有三个容易混淆、但必须区分的概念：

- **不是简单共享聊天记录。** 外部 Agent 可以保留自己的对话和上下文。重点是它能控制我们的工作环境、任务和执行过程，并拿到可继续决策的结果。
- **不是把我们的客户端嵌入别人的客户端。** 我们的客户端仍然是独立产品，负责本机项目、执行环境和人类可见的操作界面。
- **不是只暴露几个孤立工具。** 外部 Agent 不仅要能调用文件或终端，还要能管理任务、选择工作区、使用执行模型、观察进度、获取结果并继续推进。

控制应优先通过稳定的程序接口完成，而不是依赖模拟鼠标点击和键盘输入。客户端 UI 主要服务于人类观察、管理和接管。

## 3. 三方职责必须分清

### 3.1 外部中央 Agent：负责“做什么、为什么、先做什么”

例如 Claude Code、Codex，或用户选择的其他高能力 Agent。

它负责：

- 理解用户的自然语言目标，把“许愿”变成可执行的开发目标。
- 做整体架构设计、技术选型和关键技术决策。
- 把大任务拆成有边界、可检查的小任务。
- 决定每项任务交给哪个执行模型或专业工具。
- 检查代码、测试结果和交付物，发现问题后调整方案。
- 决定什么时候继续、返工、升级执行模型或请求用户确认。

中央 Agent 使用什么模型、通过什么账号付费，由用户自己选择。我们的产品不应该强制绑定某一家高价模型，也不需要自己再造一个与它争夺决策权的中央大脑。

### 3.2 我们的 Agent 客户端与 Kernel：负责“提供环境、组织执行”

这是我们真正需要长期建设的产品能力。

客户端负责：

- 让外部 Agent 连接，并选择或打开用户授权的项目工作区。
- 提供文件、终端、浏览器、Git、编译测试等能力。
- 管理执行任务的启动、状态、暂停、取消和结果。
- 配置并调用本地执行模型，把模型请求和工具执行组织起来。
- 把工具调用、输出、错误、测试结果和交付物反馈给外部 Agent。
- 让用户在自己的客户端里看到执行过程，并能够介入或停止。

Kernel 继续保持简洁：运行必要的 Agent Loop、管理工具注册和执行、把工具结果交回执行模型。它可以让执行模型处理分配给它的局部任务，但**不负责替代外部中央 Agent 做整个项目的规划、目标管理和复杂决策**。

### 3.3 执行模型与专业工具：负责“具体干活”

默认可以使用成本较低、速度合适的模型执行：

- 按任务要求编写和修改代码。
- 修复明确范围内的 Bug。
- 完成普通重构和重复性工作。
- 根据任务要求读取文件、运行命令和整理结果。

专业工具负责更适合程序确定性完成的事情：

- 文件读写、搜索和 Diff。
- 终端命令和进程管理。
- 浏览器操作。
- Git 操作。
- 编译、测试、格式检查和其他自动化验证。

执行模型不是永远只能用便宜模型。如果局部任务很难，外部中央 Agent 可以要求换成更强的执行模型，或者自己重新分析后拆分任务。

### 3.4 用户：负责目标、授权和最终判断

用户不需要亲自安排每一个文件怎么改，但仍然应该能够：

- 提出目标和约束。
- 选择项目和模型服务。
- 查看任务、日志、Diff、测试和交付物。
- 在关键节点纠正方向、暂停或取消执行。
- 对重要操作进行授权，并决定最终是否验收。

“许愿式编程”不等于放弃监督，而是把繁琐的技术执行交给 Agent 协作完成。

## 4. 强模型与廉价模型如何配合？

两种模型的职责独立配置：

| 角色 | 主要工作 | 模型策略 |
| --- | --- | --- |
| 外部中央 Agent | 需求理解、架构、拆任务、技术决策、审查 | 可以使用高能力、高成本模型 |
| 客户端内的执行模型 | 在明确任务范围内写代码、修复和执行 | 默认优先考虑低成本模型，必要时可以更换 |

这项能力**必须纳入第一阶段基础设计**，不能再拆成一个独立的“第二阶段模型调度系统”。

第一阶段只需要把基础能力做好：

- 执行模型可以独立于外部中央 Agent 配置。
- 用户可以选择模型服务和具体模型。
- 外部 Agent 能够在任务层面指定或切换执行模型。
- 执行结果能够返回给外部 Agent，由它决定下一步。

第一阶段不需要复杂的自动模型路由、价格预测或一套庞大的调度算法。**由外部中央 Agent 判断任务难度和是否升级模型，我们的客户端提供清晰、可靠的模型调用能力即可。**

## 5. 核心架构原则

### 原则一：智能与执行解耦

中央决策模型、执行模型和工作环境不绑定同一家厂商。更换外部 Agent 或模型，不应该要求推翻客户端和 Kernel。

### 原则二：客户端首先是可被 Agent 操控的工作环境

外部 Agent 应当能够通过程序接口完成工作，而不是只能打开一个聊天窗口，或者依赖 UI 自动化模拟人类点击。

### 原则三：先定义能力契约，再确定接入协议

需要先明确外部 Agent 能做什么、参数是什么、结果如何返回、失败如何表达，再选择接入方式。

API、MCP、SDK、事件推送等可以作为不同适配方式研究。MCP 可以承担工具接入，但不能默认认为它单独解决了任务生命周期、执行状态、权限和事件恢复等全部问题。具体协议组合暂不在本文中锁定。

### 原则四：Kernel 不重复建设中央大脑

不在 Kernel 内再堆一套复杂的项目规划器、Goal Loop、Workflow Runtime 或中央 Agent。外部中央 Agent 负责整体决策，Kernel 保持必要的执行循环和工具边界。

### 原则五：执行过程必须可观察、可接管

外部 Agent 需要拿到结构化的任务状态和执行事件；用户需要在客户端看到发生了什么。断线后至少应能重新查询任务状态和已有执行结果，不能让关键状态只存在于某个 UI 进程的内存里。

### 原则六：安全边界不能省略

外部 Agent 一旦能够操作本机文件和终端，就相当于获得了真实执行能力。因此至少需要：

- 对外部连接进行身份认证。
- 明确外部 Agent 被授权操作的项目和能力范围。
- 记录关键操作及执行结果，便于追溯。
- 提供用户暂停、取消和必要的确认入口。
- 需要隔离时优先使用操作系统账户、容器或虚拟机等环境边界。

这不是要求在 Kernel 中重新造一套复杂的权限系统。具体隔离方式应放在合适的宿主和运行环境边界中设计。

## 6. 实施范围：第一阶段就把模型执行纳入基础能力

第一阶段的目标是跑通一条完整、可观察、可接管的链路：

**一个外部中央 Agent + 我们的客户端 + 一个本地执行模型 + 一组专业工具。**

第一阶段需要考虑：

1. 外部 Agent 的连接与控制接口。
2. 项目工作区的选择和管理。
3. 文件、终端、浏览器、Git 等基础执行能力。
4. 本地执行模型的配置、调用和基本切换能力。
5. 任务启动、状态查询、暂停、取消和结果返回。
6. 工具调用、执行日志、错误和测试结果的事件反馈。
7. 用户在客户端中的观察、授权和接管。
8. 必要的身份认证、操作记录和环境隔离边界。

这些是同一条基础链路上的组成部分，不是先做客户端、再单独做模型调度、最后才让外部 Agent 接入。

## 7. 后续再考虑多 Agent 协作

第一阶段先验证单个外部中央 Agent 能否稳定指挥一条执行链。它跑通以后，再根据真实需求扩展：

- 多个执行 Agent 分别负责前端、后端、测试等工作。
- 独立工作区或 Git Worktree，避免多个 Agent 同时修改同一份文件。
- 任务依赖、并行执行和结果汇总。
- 代码冲突处理、交叉审查和统一验收。

这些属于后续扩展，不应该成为第一阶段的前置条件。没有真实需求和验证结果之前，不提前建设 Agent Teams、复杂并行调度和大型工作流系统。

## 8. 明确不做的事情

为了避免项目再次膨胀，当前方向明确不追求：

- 让 Kernel 自己取代外部强模型，成为全项目的中央架构师。
- 强制用户购买我们的高价模型服务。
- 第一阶段就实现复杂的自动模型路由和价格优化算法。
- 第一阶段就实现多个 Agent 的并行开发团队。
- 用 UI 鼠标自动化代替稳定的程序控制接口。
- 为了支持外部 Agent 而重写现有最小 Agent Loop。
- 把本文描述的目标能力写成当前已经实现的功能。

## 9. 与当前 Kernel 的关系

当前内核仍然遵循：

~~~text
模型决定下一步
    ↓
Kernel 执行 Tool
    ↓
Tool Result 返回模型
    ↓
模型继续决定
~~~

未来的外部中央 Agent 位于更外层，负责项目级目标、任务安排和结果审查；客户端内的执行模型负责被分配任务中的具体工作。两者分工不同，不需要在 Kernel 中再造一套项目级中央决策循环。

本文是未来产品方向，不是当前实现说明。判断当前到底支持哪些能力，仍然以代码、测试和 [当前架构文档](../architecture.md) 为准。进入实际功能开发时，必须另行提交接口、模块边界、验收标准、测试和风险方案，并按项目研发流程确认后再实现。

## 最终定位

**用户提出目标，外部强模型负责指挥，我们的 Agent 客户端提供统一工作环境并组织执行，廉价模型和专业工具完成具体工作，用户始终可以观察、干预和验收。**
