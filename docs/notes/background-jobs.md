# 后台任务的踩坑记录

`shell` 的 `background` 只做了一半：能起、不能看、不能停。补 `shell-output` / `shell-kill` 的过程里踩了五个坑，四个是进程与句柄，一个是测试自己骗自己。同样是「现象 → 根因 → 解法」。

## 1. 管道接输出，宿主进程退不出去

- **现象**：后台进程用 `stdio: ["ignore", "pipe", "pipe"]` 接输出，`child.unref()` 也调了，但宿主任务跑完后进程不退出，只能等外部硬杀。
- **根因**：`unref()` 只解除 `ChildProcess` 那个句柄的引用，管道本身的 handle 仍然挂在 event loop 上。有管道、有监听，event loop 就一直有活干。
- **验证方式**：写一个只做「spawn + unref + 监听 data」的脚本，用 `timeout 6` 跑它。退出码 `124` 说明它被卡住了；换成写文件，退出码 `0`。
- **解法**：输出写文件（`stdio: ["ignore", fd, fd]`），父进程立刻 `closeSync(fd)`。父进程一个句柄都不留，`unref()` 的语义才真的成立。
- **防复发**：`test/workspace.test.mjs` 的「后台执行」用例断言调用立即返回；更根本的是这里根本没有管道可挂。

## 2. Windows 上 `shell:true` + `detached:true` 会把输出整个吞掉

- **现象**：日志文件永远是 0 字节，子进程 `exit 0`，看起来一切正常。
- **根因**：Windows 上 `detached: true` 走 `DETACHED_PROCESS`（没有控制台），再叠加 `shell: true` 的 `cmd.exe` 包装层，cmd 的输出落不到传进去的 fd 上。
- **排查过程**：矩阵测试五个组合——`exec+detached` ✅ 5000 字节、`shell` ✅ 5000、`shell+detached` ❌ 0、`shell+detached+hide` ❌ 0。改成 shell 自己的 `> file 2>&1` 重定向**也一样是 0**，所以问题不在句柄传递，而在 `shell+detached` 这个组合本身。
- **解法**：`detached: process.platform !== "win32"`。POSIX 需要进程组（`kill -- -pid` 收整棵树），Windows 靠 `taskkill /T` 走父子关系，本来就不需要 detached。
- **防复发**：前台 `run()` 早就是这条规则，两处必须一致——这是「同一条规则写在两处就会漂移」的实例。用例「读到输出后，第二次只返回新增的部分」会立刻发现 0 字节。

## 3. 按字节偏移读日志，会把汉字切成两半

- **现象**：日志末尾刚好是一个多字节字符的前两个字节时，`toString("utf8")` 产出替换字符 `�`；下一次又从中间接着读，一个字坏两次。
- **根因**：游标是字节偏移，而字符是变长的。文件被写入方分块 flush 时，任何时刻都可能停在一个字符中间。
- **解法**：`completeUtf8Prefix()` 回退最多 3 个字节找到起始字节，末尾不完整的部分**不消费**，游标不动，等它补齐。
- **连带坑**：只做上面这一步还不够。等待循环的条件是「有新字节就返回」，而「只有半个字符」也满足「有新字节」——于是第一次返回空、第二次立刻又返回空，永远等不到补齐。循环必须改成「读到**完整字符**才返回」。
- **防复发**：用例「被切断的多字节字符不会读成替换字符，补齐后才返回」先写两个字节、由测试写文件触发第三个字节，断言第一次不含 `�` 也不含「中」，第二次含「中」。

## 4. 增量游标推过头，模型就再也看不到那段内容

- **现象**（差点写出来）：一次读 32 KB、截断到 8k 字符返回，游标却按 32 KB 推进——中间 24 KB 永久丢失。
- **根因**：把「读了多少」和「给了多少」当成同一件事。
- **解法**：游标只推进**真正返回的字节数**（`Buffer.byteLength(shown)`），剩下的留在日志里，末尾明说 `… [N chars not shown; call shell-output again]`。
- **防复发**：用例「单次最多 8000 字符」断言第二次能读到剩下的 1000 个字符，且不再提示「还有」。

## 5. 测试里断言失败被清理阶段的 EBUSY 盖住

- **现象**：用例报 `EBUSY: resource busy or locked, rmdir ...`，看起来像「目录删不掉」，实际是断言先失败了。
- **根因**：断言抛异常 → `withWorkspace` 的 `finally` 立刻 `rm` → 后台进程还活着、cwd 就指着那个目录 → `rm` 抛 EBUSY，**替换掉了原始异常**。
- **解法**：后台用例统一 `try { ... } finally { await stopJob(...) }`，先停进程再让清理跑；`stopJob` 自己吞掉收尾异常，不盖住真正的失败。
- **连带教训**：进程 pid 不响应信号（`ESRCH`）不等于系统已经释放它的 cwd。`killJob` 因此要等 `exit` 事件再回答，否则宿主紧接着删目录照样 EBUSY。

## 6. 状态行会把命令原样带出来

- **现象**：断言「第一次读不该出现 second」失败，但测试里 `second` 明明还没产生。
- **根因**：`shell-output` 第一行是 `job-1 (running, pid N) ran: <原命令>`，而原命令里就写着 `console.log('second')`。
- **解法**：正文断言只看状态行之后的部分（测试里的 `body()`）；这也是产品上的取舍——状态行带命令是为了让模型确认「这是哪个任务」，不能为了好断言把它删掉。
- **教训**：断言一个「不该出现」的字符串时，先确认它没有出现在回显里。
