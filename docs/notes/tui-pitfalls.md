# TUI 踩坑记录

每一条都是真实发生过的：现象 → 根因 → 解法。做新渲染层或前端时先读一遍，这些坑与呈现技术无关，是信息模型的问题。

## 1. 备用屏：看不见打开之前的命令

- **现象**：`agent` 一开就是全新界面，之前敲的命令看不到，退出才回来。
- **根因**：进了终端的备用屏（`ESC[?1049h`），那是一块独立画布。
- **解法**：主视图改为在主屏就地追加，已定稿的行打印一次进 scrollback；备用屏只留给 `Ctrl+T` 的 transcript 视图。
- **同类**：Claude Code 的 `<Static>`、Codex 的 inline viewport。

## 2. 提交游标按「行数」计数，折叠后整体错位

- **现象**：轮次结束后出现重复行、空行消失、内容整段不见。
- **根因**：用 `printedLines`（打印到第几行）做游标；折叠会让行数变少，游标越过实际长度，之后的行要么被跳过，要么被重打。
- **解法**：不靠计数猜位置。能改就改成「最后一条已打印行的身份」重新对齐；不能改时要接受「已打印即定型」。
- **教训**：任何「第 N 行」的状态，都假设了内容只会追加。一旦内容可能变短，这个假设就破产。

## 3. 空白行被当成「过程」隐藏

- **现象**：折叠后用户消息、回复、状态行三行挤在一起，没有间距。
- **根因**：空行是日志条目，被打上了本轮 `turn` 标记；折叠时和工具行一起被过滤掉。
- **解法**：空行不是过程输出，是块与块之间的呼吸。折叠时保留，连续空行压成一行。

## 4. 一次性提示写进持久日志

- **现象**：按住 `Ctrl+E`，屏幕上刷出十几行「这一轮已经打印完成…」。
- **根因**：提示走 `logLine`，等于写进 scrollback；按一次追加一行。
- **解法**：一次性提示属于活动区（可重绘），不属于历史。要么做成短暂显示，要么直接给动作（打开 transcript），不要往日志里写。

## 5. 状态行排在用户消息和回复之间

- **现象**：`已完成 · 用时 4 秒` 出现在回复上面，读起来像「还没开始就说完成了」。
- **根因**：状态行在 `beginTurn` 时就进了日志，位置固定在用户消息之后。
- **解法**：状态行是这一轮的结果，必须排在回复之后。运行中的状态只作为活动区尾部显示，结束时才落账。
- **参照**：Claude Code 的 `✻ Cooked for 12s`、Codex 的耗时都在回复下面。

## 6. 鼠标捕获与原生滚轮互斥

- **现象**：想支持点击展开，结果滚轮滚不动历史。
- **根因**：开 `ESC[?1000h` 后滚轮事件变成鼠标报告发给程序，终端不再自己滚 scrollback；协议层面没有「把滚轮还给终端」的办法。
- **解法**：不捕获鼠标。滚轮、滚动条、选中复制保持原生；展开走键盘 + 独立视图。
- **同类**：Claude Code 和 Codex 都不捕获鼠标。

## 7. 绝对定位泄漏到主视图

- **现象**：屏幕上出现两个输入框。
- **根因**：`readLine` 里用 `ESC[inputRow;1H` 把光标搬回输入行——那是整屏网格的假设，主视图是相对定位。
- **解法**：主视图不碰绝对行号；`moveToInput` 只在 transcript 视图里生效。

## 8. 测试按「第几行」断言

- **现象**：每次调整布局，几十条测试一起红，逼着人去改产品迁就测试。
- **根因**：断言整屏快照和绝对行号，把实现细节当成了契约。
- **解法**：按内容定位（`rowWith(ui, /Thinking/)`、`inputLine(ui)`、`statusLine(ui)`）；只有协议级事实（进不进备用屏、捕不捕获鼠标）才断言转义序列，并写清为什么。

## 9. 已打印的内容想原地展开

- **现象**：点历史轮次的箭头，内容要么不出现，要么重复刷屏。
- **根因**：scrollback 不可回改，插入行做不到。
- **解法**：主视图不提供历史展开；历史详情去 `Ctrl+T` 的 transcript 视图。这也是两家的做法。

## 10. 没有可展开内容却显示展开入口

- **现象**：纯问答也显示 `已完成 · 用时 5 秒 ▸ （Ctrl+E 展开）`，点开什么都没有。
- **根因**：状态行无条件打印，箭头暗示了不存在的操作。
- **解法**：状态行只在「这一轮真的有折叠的过程层」时出现；失败/取消例外，那是结果本身。

## 11. 详情视图从来没画过内容

- **现象**：按 `Ctrl+E` / `Ctrl+T` 进 transcript，屏幕一片空白，什么都看不到。而主视图一直在提示「详情请按 Ctrl+T 查看」。
- **根因**：`renderTranscript()` 的入口守卫写成了 `if (!this.started || !this.closed) return;`——意思是**只有关闭之后才画**。少了一个 `!`，整个视图从未渲染过。
- **解法**：改成 `if (!this.started || this.closed) return;`，并补一条测试：进入 transcript 后必须能读到历史内容，不能只断言「进了备用屏」。
- **教训**：这是最贵的一类 bug——**功能看起来存在，实际是空的**。当时所有测试都在断言「按了键会发 `ESC[?1049h`」，没有一条断言「进去之后能看到东西」。断言入口不等于断言结果。

## 12. 运行态把同一件事说了三遍

- **现象**：一轮带工具的对话，活动区六行里只有一行是有效信息：
  ```
  + 列出 .
    o 已读取文件 你好世界.txt。   ← 和下一行说同一件事
  + 读取 你好世界.txt
  * Thinking... (3s · 2 个工具结果)
  + Ctrl-C 取消
    o 正在执行 · 已用时 9 秒       ← 和 Thinking 说同一件事
  ```
- **根因**：三种信息源各自独立渲染——工具事件、自然语言概述、运行状态。它们描述的是同一个事实，但没人负责去重。
- **解法**：主视图只保留「工具行」，等待时只保留 Thinking 一行（它已经带了秒数、工具结果数），取消提示并进这一行；概述只留在 transcript。
- **教训**：**每个视图要有唯一的「事实来源」**。多个组件都能说「正在读取文件」时，用户看到的就是三遍。拍平不只是去掉缩进，是去掉重复叙述。

## 13. 运行中往上翻不动历史

- **现象**：一轮任务在跑的时候，想往上翻看之前的对话，翻不上去，视口总被拉回底部。
- **根因**：主视图在主屏就地追加，滚动本该交给终端。但运行中我们每秒都在重画活动区（`\x1b[NA` + `\x1b[J` + 重打尾部），终端会把视口跟着输出拉回底部。而且 `PgUp` 被 readline 吞掉，终端自己的翻页也失效。
- **解法**：`PgUp` 冻结活动区重绘（打印一行「已暂停刷新」，之后不再往底部写），用户可以自由用滚轮翻看；`PgDn` 或 `Esc` 恢复。输入框仍然强制重绘，打字不会看不见。
- **业界**：这是这一类 TUI 的通病，不是我们独有。Claude Code 挂着一串同源 issue（#826 / #769 / #1486 / #367 / #33814，统称「TUI 渲染导致意外滚动」），社区给的办法是用 tmux（tmux 自己管视口，不受程序输出影响）。**没人根治**，所以我们做的是「给用户一个暂停开关」，而不是假装解决了。
- **教训**：当产品跑在别人的画布上（终端 scrollback）时，**控制权不在我们手里**。能做的是「少写、能停」，而不是「接管滚动」。

## 14. 粘贴一段多行文本，被当成多次回车

- **现象**：把一段对话粘进输入框，它没有变成一条消息，而是一行一行地发出去，每一行都触发一轮任务。
- **根因**：没有开启括号粘贴（bracketed paste）。终端只能把粘贴内容原样送进来，里面的换行就是 `\r`，readline 逐行当作提交。
- **解法**：启动时发 `ESC[?2004h`（退出时 `ESC[?2004l`），终端就会把整段粘贴包在 `ESC[200~ ... ESC[201~` 之间；在这对标记之间的换行是内容，不是提交。多行内容整段收下，输入框只显示一行占位提示（`[已粘贴 12 行]`），提交时把原文交给模型。
- **教训**：终端里的「换行」有两种含义（内容 vs 提交），**只有括号粘贴能区分**。任何多行输入需求都必须先打开这个模式。

## 15. 审批菜单一弹出，上面的日志就一行一行被吃掉

- **现象**：长任务跑到一半弹出 Shell 审批菜单，菜单停在那儿等按键，而它上面的日志**每秒少一行**。等待越久，历史越短，看着像内容自己在往回收。
- **根因**：主视图每帧的写法是「上移 N 行 → 擦到行尾 → 重打活动区」。N 由 `rowsAboveInput` 算，公式是「活动区行数 + 输入框上边框 + (输入行数 - 1)」，**前提是光标停在输入行上**。但审批时输入框被菜单顶掉，光标锚点变成了那条分隔线——它上面只剩活动区。公式没跟着分支，于是每帧多上移一行，把上一行历史擦进 `\x1b[J` 的清除范围里。活动计时器每秒重绘一次，所以是**一秒一行**。
- **为什么难发现**：`\x1b[J` 擦掉的内容是已经打印出去的历史，终端里看不回来，也没有任何报错。它只在「审批 + 上方有已定稿历史 + 至少重绘两次」三条同时成立时出现，短任务和纯对话都碰不到。
- **解法**：`rowsAboveInput` 跟着帧的布局分支走——审批时锚点是分隔线，只上移活动区行数；有输入框时才是「活动区 + 上边框 + 输入行数 - 1」。
- **防复发**：用例「审批期间重绘不能吃掉已经打印的历史行」先铺 12 行历史、再进审批、然后**等两个真实的计时器周期**，断言历史行数不变。第一版用例用 `resize` 触发重绘，结果 resize 有防抖、渲染根本没跑，测试假绿——**触发方式必须和生产里真正的那条一致**。

## 归纳：四条底层规则

1. **追加即定型**：打印出去的行不会变。所有交互设计都要先问「这条内容还能改吗」。
2. **一次性 vs 持久**：提示、状态、进度属于活动区；结果、错误、对话属于历史。放错地方就会刷屏或丢失。
3. **克制主视图**：概览层只回答「发生了什么」，详情另开视图。终端受限于物理约束，前端即使有能力也不该默认全展开。
4. **断言结果，不只断言入口**：测「按了键会进备用屏」是不够的，还要测「进去之后看得到东西」。功能看起来存在、实际是空的，是最贵的一类 bug。
