# CLI 与工程链路的踩坑记录

TUI 之外的坑：命令行参数、全局安装、测试迁移。同样是「现象 → 根因 → 解法」，动这些地方前先读一遍。

## 1. 在目标目录里跑 `npm run agent` 报 ENOENT

- **现象**：`cd C:\...\测试` 后执行 `npm run agent -- ...`，报 `Could not read package.json`。
- **根因**：npm 只认**当前目录**的 `package.json`；`--cwd` 是传给 agent 的参数，管不到 npm。
- **解法**：给包加 `bin` 入口，`npm link` 装成全局命令 `agent` / `agent-kernel`，在任意目录直接跑，工作区就是当前目录。
- **教训**：工具的使用方式和工具的配置参数是两回事，别指望参数去影响调用方。

## 2. `npm link` 装到了错误的 Node 前缀

- **现象**：装完命令，在用户自己的 cmd 里仍然「不是内部或外部命令」。
- **根因**：第一次 link 用的是工具链自带的 Node（`...\.workbuddy-ai\binaries\node\...`），shim 落在那个前缀；用户 PATH 里的是 `E:\develo\nodejs`，全局目录为 `%APPDATA%\npm`。
- **解法**：用**用户自己的 npm** 执行 link；给用户装全局命令时先确认 `npm config get prefix` 和 PATH 顺序。
- **教训**：涉及 PATH 的操作，必须先问「哪个 node/npm 在生效」。

## 3. PATH 里 0 字节的 `.cmd` 静默遮蔽真命令

- **现象**：敲 `agent` 什么都不发生，也没有报错。
- **根因**：`E:\develo\nodejs\agent.cmd` 是个 0 字节文件（之前某次 `>` 被当成重定向留下的），而机器级 PATH 排在用户 PATH 前面。
- **解法**：删掉空壳；装完命令后确认 `where agent` 指向 `%APPDATA%\npm\agent.cmd`。
- **教训**：空文件不会报错，只会让命令「安静地不工作」。排查时先 `where`，再看文件大小。

## 4. 粘贴命令行时带上了提示符

- **现象**：`C:\...>C:\...>agent --tui` 报「不是内部或外部命令」，还在目录里生成了一个 0 字节的 `agent` 文件。
- **根因**：复制时把提示符一起复制了，`>` 被 cmd 当成**重定向**，后面的词被当成文件名。
- **解法**：只复制命令本身；看到莫名出现的 0 字节文件，先怀疑重定向。
- **教训**：终端里的 `>` 有两种含义，粘贴时最容易踩。

## 5. 删掉 `--repl` 后它被当成任务文本

- **现象**：如果只删解析分支，`agent --repl` 会变成「任务名叫 `--repl`」发给模型。
- **根因**：`parseArgs` 里未知参数会落进 `taskParts`。
- **解法**：删除开关时必须**显式拦截**并报错，同时加一条测试断言「不产生模型请求」。
- **教训**：删除功能比新增功能更危险——静默降级比报错难查。

## 6. 测试夹具只认绝对光标

- **现象**：主视图改成相对定位后，132 条 TUI 测试挂了 95 条。
- **根因**：测试里的虚拟终端只解析 `ESC[n;1H` 和 `ESC[2J`，不认识 `ESC[nA`、`\r`、`ESC[J`。
- **解法**：先升级夹具（支持相对移动、清行、清到屏尾、滚动），一次救回 53 条，再逐条改断言。
- **教训**：夹具的能力决定了测试的表达力；模型换了，夹具也得跟着长。

## 7. 测试断言写死行号

- **现象**：每次布局调整，几十条测试一起红，逼着改产品去迁就测试。
- **根因**：断言的是「第 18 行是输入框」这种实现细节。
- **解法**：改成按内容定位（`rowWith` / `inputLine` / `statusLine`）；只有协议级事实才断言转义序列。
- **教训**：测试是规格，规格该描述行为，不该描述像素。

## 8. 边跑测试边改源码

- **现象**：`npm test` 偶发 1 条失败，重跑就绿。
- **根因**：后台跑测试时同时在编辑 `src/`，Node 读到写了一半的文件。
- **解法**：改完再跑，或等后台任务结束；失败先重跑一次确认是否稳定复现。
- **教训**：并发改文件和跑测试是自找的 flaky。

## 9. 用「猜」代替查证

- **现象**：为了修间距，先后猜了「宽度不对」「游标漂移」「折叠导致」，改了三轮都没修对。
- **根因**：没有先定位现象和参照对象，直接改代码。
- **解法**：先看同类产品怎么做（Claude Code / Codex），再对照自己的输出定位；结论要能落到「它把 X 放在 Y 之后」这种可验证的句子。
- **教训**：猜出来的修法只能算补丁，而且会让下一次定位更难。

## 归纳

1. **调用方与工具要分清**：npm 的 cwd、PATH 里的 node、粘贴进去的提示符，都不是工具能控制的。
2. **静默失败最贵**：空文件、被吞掉的参数、只认一半转义的夹具——都要靠显式校验和测试盯住。
3. **先查证再动手**：同类产品怎么做、现象到底是什么，比「我觉得应该」可靠。
