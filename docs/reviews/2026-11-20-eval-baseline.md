### 3.1 通过分布

| 类别 | 任务数 | 说明 |
| --- | ---: | --- |
| 三轮全通过 | 19 | 所有代码类任务，57/57 |
| 三轮全失败 | 1 | `04-create-doc`（0/3） |
| 偶发失败（1–2 轮） | **0** | 本次采样没有出现真正的抖动 |

**没有任何任务出现「这轮过、下轮不过」。** 60 次执行只分出两种结局：19 个任务 100% 通过，1 个任务 100% 失败。这比 95% 这个数字本身更有信息量——它说明当前内核在这批任务上不是「差不多能做对」，而是「要么会、要么不会」。

### 3.2 `04-create-doc`：重复失败，成因确定

三轮报错都落在同一个分支：

```
文档表格必须逐项列出 package.json 的全部 npm scripts
+ actual - expected
+ []
- [ 'lint', 'test' ]
```

`documented` 为空，说明表头与分隔线的断言都过了，但**一行数据都没被解析出来**。

为确定机制，用六种表格形态直接调用该任务的 `check.mjs`（只读实验，未修改检查器）：

| 形态 | 结果 |
| --- | --- |
| A 两列，表头 `\| 命令 \| 说明 \|`，命令写 `npm run test` | **PASS** |
| B 三列，表头 `\| 命令 \| 实际执行 \| 说明 \|` | FAIL：正文必须有 Markdown 表格分隔线 |
| C 三列，表头 `\| npm script \| 命令 \| 说明 \|` | FAIL：正文表格必须有命令列和说明列 |
| D 两列表头 + 三列数据行 | FAIL：文档表格必须逐项列出…（`[]`） |
| E 两列，命令列只写脚本名 `test` | FAIL：文档表格必须逐项列出…（`[]`） |
| F 两列，`npm test` / `npm run lint` | **PASS** |

另外用 `--keep --trace` 单独跑了一次该任务（记录：[diagnostics/04-create-doc-trace-2026-11-20.json](../../eval/baselines/2026-11-19-checkers-v2/diagnostics/04-create-doc-trace-2026-11-20.json)），保留的产物是 **C 形态**（三列、表头首列 `npm script`）：

```markdown
# 用法

| npm script | 命令 | 说明 |
| --- | --- | --- |
| `test` | `node --test` | 运行项目内的测试文件。 |
| `lint` | `node --check .` | 检查项目代码的语法错误。 |
```

**判断**：检查器只接受「两列 + 首列表头恰好叫 `命令` + 命令列写成 `npm (run )?<script>`」。任务描述写的是「表格列出每个 npm script（命令 + 一句说明）」——把脚本名单独列一列是**对需求的合理扩展**，产出的文档质量并不差，但它落在检查器接受集之外。三轮失败中 D/E 两种形态都能复现同一报错，无法从记录反推是哪一种（工作区已清理），但都属于同一类「形状不符」。

**这次失败不是能力问题，是契约问题。** 它同时解释了为什么单独复跑能通过：那次恰好写成了 A/F 形态。**单次复跑通过不能作为「任务其实能做」的证据，也不能据此把成绩改成 20/20。**

逐任务三轮 Token 波动（`spread` = max / min）：

| 任务 | 三轮 Token | 波动 | 三轮请求数 |

同样的任务、同样的初始文件，请求数会在 4 到 9 之间摆动，Token 随之翻倍。这是**规划路径的随机性**，不是环境抖动：成功的任务里，模型有时 4 步收敛，有时先探索再收敛。预算估算必须按中位数留余量，不能按最好一轮。

### 3.4 墙钟

第 1 轮 91.8 秒，比第 2、3 轮（78.8 / 79.5 秒）慢 16%。三轮并发都是 4，任务耗时合计也只差 19%（326.7 / 274.8 / 286.0 秒）。最可能的解释是首次运行时的冷启动（进程、文件系统缓存、模型端预热），但**本次没有做对照实验，这只是推断，不是结论**。

## 4. Token 成本分析

### 4.1 成本构成（实测，不是估算）

用两个探针分别量出固定块的 token 占用（每次请求都会带上，与任务无关）：

| 组成 | 字符数 | Prompt tokens | 占固定块 |
| --- | ---: | ---: | ---: |
| 控制组（空内容基线） | — | 23 | — |
| 系统提示 `DEFAULT_SYSTEM_PROMPT` | 7,753 | **1,600** | 44.8% |
| 9 个工具的定义（线上 JSON） | 7,987 | **1,972** | 55.2% |
| 合计 | 15,740 | **3,572** | 100% |

交叉验证：`--trace` 记录里第一次请求（只有 system + user 两条消息）`messageChars` 8,021、`toolDefinitionChars` 7,708、`promptTokens` 3,660。3,572（固定块）+ 23（基线）+ 约 65（任务描述 268 字符）≈ 3,660，与实测吻合。注意 `toolDefinitionChars` 量的是内部 `ToolDefinition[]`（7,708 字符），上面表格量的是发给端点的线上 JSON（多一层 `{type, function}` 包装，7,987 字符），两者差 279 字符，不是矛盾。

工具定义按体积排序（线上 JSON 字符数）：

| 工具 | 合计 | 参数 Schema | 描述文本 |
| --- | ---: | ---: | ---: |
| `read` | 1,714 | 644 | 993 |
| `shell` | 1,432 | 480 | 874 |
| `grep` | 1,116 | 594 | 439 |
| `write` | 851 | 270 | 503 |
| `edit` | 849 | 410 | 362 |
| `glob` | 731 | 334 | 316 |
| `shell-output` | 536 | 260 | 191 |
| `ls` | 402 | 225 | 102 |
| `shell-kill` | 346 | 142 | 121 |

`read` + `shell` 两个工具占了工具开销的 39.4%，其中光是描述文本就有 1,867 字符。

### 4.2 固定块吃掉多少

| 口径 | 数值 | 占比 |
| --- | ---: | ---: |
| 平均每请求 Prompt | 4,010 tokens | 100% |
| 其中固定块 | 3,572 tokens | **89.1%** |
| 其中任务描述 | ~60 tokens | 1.5% |
| 其中历史对话 + 工具结果 | ~378 tokens | 9.4% |
| 全部 Token 中固定块贡献 | 397 × 3,572 = 1,418,084 | **87.0%** |
| Completion 占全部 Token | 38,825 | 2.4% |

**结论：Token 账单的 87% 是把同一段 3,572 tokens 的内容重复发了 397 次。** 对话历史增长、工具返回、模型输出加在一起只占 13%。

### 4.3 历史增长不是问题

单个任务 7 次请求的 prompt 变化（`04-create-doc` 诊断运行）：

| 请求 | 消息数 | 消息字符 | Prompt tokens |
| ---: | ---: | ---: | ---: |
| 1 | 2 | 8,021 | 3,660 |
| 2 | 5 | 8,721 | 3,762 |
| 3 | 7 | 9,148 | 3,829 |
| 4 | 10 | 10,095 | 3,975 |
| 5 | 13 | 10,739 | 4,085 |
| 6 | 15 | 11,590 | 4,186 |
| 7 | 17 | 11,970 | 4,256 |

6 轮对话只让 prompt 涨了 596 tokens（每轮约 99）。历史累积是次要项，**不是成本主因**。

### 4.4 工具返回结果也不是大头

同一次运行 9 次工具调用的返回字符数：115、12、91、52、250、127、26、32、32，合计 **737 字符（约 200 tokens）**。工具返回在这个任务里连 1% 都不到。

### 4.5 与旧 v2 基线的差异归因

旧 v2（`eac798d`，2026-11-05，中位数 89.5 请求 / 118,817 tokens）用同样的方法测过固定块：

| 组成 | 旧 v2（`eac798d`） | 当前（`76a024a`） | 倍数 |
| --- | ---: | ---: | ---: |
| 系统提示字符 | 654 | 7,753 | 11.9× |
| 系统提示 tokens | 135 | 1,600 | 11.9× |
| 工具数 | 7 | 9 | 1.3× |
| 工具定义字符 | 2,679 | 7,987 | 3.0× |
| 工具定义 tokens | 757 | 1,972 | 2.6× |
| **固定块 tokens** | **892** | **3,572** | **4.0×** |
| 请求数（中位数） | 89.5 | 132 | 1.47× |
| 每请求 Token | 1,328 | 4,110 | 3.10× |
| 单轮 Token | 118,817 | 542,515 | 4.57× |

分解：4,110 / 1,328 = 3.10 倍（单请求），乘 1.47 倍（请求数）= 4.56 倍，与 4.57 倍吻合。

单请求增加 2,782 tokens，其中固定块贡献 **2,680 tokens（96.3%）**；历史 + 输出的可变部分只增加了约 102 tokens（436 → 538，+23%），对单请求涨幅的贡献不到 4%。也就是说：**模型没有变啰嗦，是提示词和工具说明变长了 4 倍，然后被乘以更多次请求。**

⚠️ 归因边界：旧 v2 用的是旧检查器套件，任务集与验收口径有变化，所以「请求数 +47%」这一项**不能单独归因于内核**；但「固定块 892 → 3,572」是同一套测量方法在同一份代码上的差异，属于内核侧变化，可直接比较。

### 4.6 已知证据 vs 需要进一步验证

**已有证据（可直接引用）**

- 固定块 = 1,600（系统提示）+ 1,972（工具定义）tokens，每请求必带，占全部 Token 87%。
- Completion 只占 2.4%。
- 历史对话在 7 步内只增加约 596 tokens。
- 单任务工具返回合计约 700 字符量级。
- 工具定义中 `read` / `shell` 的描述文本是最大单项。

**推断（未经实验验证）**

- 第 1 轮慢 16% 是冷启动。
- 请求数从 89.5 涨到 132 与提示词变长有关（提示词鼓励了更多验证步骤），但套件不同，无法分离。
- 3,572 tokens 的固定前缀在 397 次请求中高度重复，理论上前缀缓存能显著降低成本——**但这只是理论，本次没有任何缓存命中数据**。

**缺少的观测能力（这是本次分析的真实边界）**

| 缺什么 | 为什么需要 | 现状 |
| --- | --- | --- |
| 逐请求明细进正式基线 | 三轮 60 次执行里只有 1 个任务开了 `--trace`，其余只能用「总量 ÷ 请求数」反推 | `run.mjs` 仅在 `--trace` 时写 `trace` |
| 前缀缓存命中 | 端点已返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，但 `src/model/llm.ts` 的 `readUsage` 只读三个总量字段，缓存数据被丢弃 | 未采集 |
| 工具级失败率 | 基线只记录「执行了多少次」，不记录每次是否失败；失败率只能靠单任务 trace 抽样 | 未采集 |
| 上下文压缩的实际成本 | 三轮都没有触发压缩，没有数据 | 未触发 |

**不能做的事**：不能拿总 Token 去反推「系统提示占 40%、工具占 30%」这种比例。上面 44.8% / 55.2% 的拆分来自独立的探针测量，不是从总量估算的。

## 5. 执行效率

| 指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 墙钟 | 91.8 秒 | 78.8 秒 | 79.5 秒 | 79.5 秒 |
| 任务耗时合计 | 326.7 秒 | 274.8 秒 | 286.0 秒 | 286.0 秒 |
| 并发利用率（合计/墙钟） | 3.56× | 3.49× | 3.60× | 3.60× |
| 请求数 | 132 | 131 | 134 | 132 |
| 工具调用 | 138 | 133 | 134 | 134 |

**并发利用率 3.6 / 4**，任务池几乎没有空转，瓶颈不在调度。

**时间花在哪**：单个任务（`04-create-doc` 诊断运行，12.1 秒）里，7 次模型往返合计 11,802 ms，占 **97.5%**；工具执行 + 内核开销合计 2.5%。单次请求平均 1,686 ms。所以墙钟 ≈ 请求数 × 模型延迟 ÷ 并发，**优化墙钟等于减少请求数，而不是优化工具实现**。

**请求数与工具调用数的关系**：405 / 397 = **1.02**。几乎每次请求只带一个工具调用，模型很少并行批量调用。这意味着「请求数 ≈ 工具调用数 ≈ 步骤数」，三个指标在当前实现里几乎是同一个东西，任何一个上涨都会等比例推高成本。

**探索冗余（有直接证据）**：`04-create-doc` 这个「读两个文件、写一个文件、改一行链接」的任务用了 9 次工具调用：

```
shell → glob → ls → ls → shell → read → read → write → edit
```

前 5 次都是探查（其中 `ls` 调了两次、`shell` 调了两次），真正必要的只有 4 次。9 次调用里 5 次是重复探查，占 55%。工具返回总量只有 737 字符，说明这些调用换回的信息极少——**成本不在返回内容，在于每次都触发一次完整请求（3,572 tokens 固定块 + 一次往返延迟）**。

| 子 Agent 委派 | **未验证** | 评测装配只注册了 9 个工作区工具，`run_subagent` 不在其中。本次 0 次委派，无法判断收益与上下文开销。 |
| 技能目录 / 项目指令注入 | **未验证** | `eval/run.mjs` 的 `systemPrompt` 直接返回 `DEFAULT_SYSTEM_PROMPT`，不注入 `AGENTS.md` 和技能目录。**真实使用时固定块会更大**，3,572 是下限。 |
| 长会话 / 多轮人工交互 | **未验证** | 每个任务都是独立单轮 run。 |
| 视觉输入、权限策略、取消与中断 | **未验证** | 评测不涉及。 |

**一句话判断**：这个内核现在「会干活、不闯祸、也不省钱」。执行层和工具层已经可靠到可以被当作基线；上下文层完全没被压到过；成本层是当前最明显的短板。

## 7. 下一阶段优化建议

按「预期收益 / 风险」排序，前两条建议优先处理。

### 7.1 给固定提示块设体积预算并瘦身（优先级：高）

**问题**：每次请求都重发 3,572 tokens 的固定块（系统提示 1,600 + 工具定义 1,972），占全部 Token 的 87%。单这一项就决定了每轮成本的下限。

**依据**：
- 探针实测：系统提示 7,753 字符 / 1,600 tokens；9 个工具 7,987 字符 / 1,972 tokens。
- `read`（1,714）与 `shell`（1,432）两个工具占工具开销 39.4%，其中描述文本 1,867 字符。
- 历史增长 7 步只有 596 tokens，说明「少说废话」不是主要抓手，**「每次少带常量」才是**。

**优化方向**：
1. 系统提示按「不可推断的规则」重写：只留工具用法约束、验证要求、结束条件；可推断的内容（如「先读再改」）删掉。
2. 工具描述去重：`read` / `shell` 的长描述里，与系统提示重复的约束合并到一处。
3. 参数 Schema 精简：检查是否有可以合并的字段、能否用更短的 `enum`。
4. 中期考虑按任务类型裁剪工具集（只读任务不带 `write` / `edit` / `shell-kill`），但这会改变行为，需单独评估。

**预期收益**：固定块从 3,572 降到约 1,800，单请求 prompt 从 4,010 降到约 2,240（**-44%**），单轮 Token 从 542,515 降到约 300,000（**-45%**）。若请求数不变，这是本轮最大的一笔节省。

**风险**：系统提示是行为的载体，删过头会直接掉通过率；工具描述变短可能让模型误用参数。改动必须视为行为变更，不能当作纯优化。

**怎么验证**：同一套件、同一提交基线、同模型跑 3 轮，看三件事——通过率不低于 57/60、每请求 prompt 中位数、`04-create-doc` 之外是否有新失败。只接受「成本降、通过率不降」的结果。

### 7.2 补齐 Token 观测：逐请求明细 + 缓存命中（优先级：高，是其他优化的前提）

**问题**：现在只有 1 个任务有逐请求数据，其余全靠「总量 ÷ 请求数」反推；端点返回的 `prompt_cache_hit_tokens` 被直接丢掉。**在看不到「哪一段花了多少」的情况下做提示词优化，等于蒙眼改。**

**依据**：
- `src/model/llm.ts` 的 `readUsage` 只读 `prompt_tokens` / `completion_tokens` / `total_tokens`。
- 端点实际返回 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`cache_read_input_tokens`。
- `eval/run.mjs` 只在 `--trace` 时把逐请求数据写进记录，正式基线不带。
- 87% 的 prompt 是重复前缀，缓存命中率直接决定真实成本，目前完全未知。

**优化方向**：
1. `readUsage` 增读缓存字段（向后兼容：字段缺失记为 unknown，不填 0）。
2. 正式评测记录里固定带上「首请求 prompt tokens + 每请求 prompt tokens 数组」这类轻量字段，不必开完整 `--trace`。
3. `summary.mjs` 增加「固定块占比」「缓存命中率」两个口径。

**预期收益**：不直接省钱，但让 7.1 的收益可归因、可回归；也为「要不要做前缀缓存优化」提供决策依据（如果命中率已经很高，7.1 的收益会被高估）。

**风险**：记录体积变大；`--trace` 有 I/O 开销，不能把带追踪的耗时当基线（现有文档已写明这一点，需要继续保持）。

**怎么验证**：跑一轮后，`summary` 能报出「固定块 tokens / 总 prompt tokens」且与本次探针测得的 89% 一致；缓存字段在缺失时显示 unknown 而不是 0。

### 7.3 压掉探索冗余，减少请求数（优先级：中）

**问题**：平均每任务 6.62 次请求，同样的任务在 4–9 次之间摆动；`04-create-doc` 的 9 次调用里 5 次是重复探查。由于墙钟 97.5% 花在模型往返上，每少一次请求就同时省 Token 和延迟。

**依据**：
- 405 工具调用 / 397 请求 = 1.02，几乎一次请求一个调用，没有批量。
- `04-create-doc` 调用序列 `shell → glob → ls → ls → shell → read → read → write → edit`，前 5 次探查只换回 737 字符。
- `05-extract-constant` 三轮请求数 8 / 4 / 9，Token 2.28 倍波动。
- 单请求平均 1,686 ms，工具执行与内核开销合计 2.5%。

**优化方向**：
1. 在系统提示里明确「先规划再动手」的边界，减少「先 `ls` 一遍看看」的试探。
2. 鼓励一次回复带多个独立工具调用（当前几乎不用）。
3. 检查是否存在「读过的文件又被读一遍」——如果上下文里有内容，提示模型不要重复读。

**预期收益**：请求数降 15–25%（132 → 100–112），Token 与墙钟同比例下降。叠加 7.1 后，单轮有望从 542,515 降到 220,000–250,000。

**风险**：少探查可能少发现边界条件，通过率下降；批量调用会让「一次失败拖垮整批」的概率上升。

**怎么验证**：3 轮评测对比「每任务请求数中位数」与通过率；同时看逐任务 spread 是否收窄（目标：最大 spread 从 2.28 降到 1.6 以下）。

### 7.4 修掉 `04-create-doc` 的契约歧义（优先级：中，但它决定了 95% 这个数字的含义）

**问题**：唯一失败的任务连续 3 轮全败，成因是表格形状契约，不是能力。只要不处理，这个 19/20 会一直跟着基线，而且**每轮都要花一次 Token 去复现同一个格式错误**。

**依据**：第 3 节的六形态实验（A/F 通过，B/C/D/E 失败）与 `--keep` 保留的实际产物（三列表格，表头 `npm script`）。

**优化方向**（二选一，不能既放宽检查又保留模糊描述）：
- **A. 收紧任务描述**：在 `task.md` 里写死「两列表格，第一列表头为 `命令`，命令写成 `npm run <script>`」。任务从此测「按格式写文档」，语义清晰但价值略降。
- **B. 放宽检查器**：接受「脚本名 + 命令 + 说明」三列，或接受命令列只写脚本名。任务保留「写清楚文档」的原意，但检查器要重写解析逻辑。

无论选哪个，都必须 **bump `EVAL_SUITE_VERSION`**，并同步更新 `test/eval-task-checkers.test.mjs` 的正反例——否则旧数据和新数据会被当成同一套件混算。

**预期收益**：消除唯一的重复失败；让「95%」不再被一个格式问题污染；若选 B，能真实反映文档能力。

**风险**：选 A 会让任务退化成格式题；选 B 会降低检查器严格度，可能放过真正敷衍的文档。

**怎么验证**：`npm run eval:check` 全绿；检查器正反例测试覆盖新形态（正例通过、三列/两列都判对、缺项仍失败）；再跑 3 轮确认 `04-create-doc` 的通过与否有稳定解释。

### 7.5 用真实场景补上「未验证」的两块（优先级：中低，但会影响后续所有结论）

**问题**：上下文压缩和子 Agent 在本次基线里**零数据**。而这两块恰好是「长任务」和「大任务」的成本与能力关键——如果它们有 bug 或开销失控，当前 57/60 完全看不出来。

**依据**：三轮最大 prompt 约 4,256 tokens，压缩从未触发；评测装配未注册 `run_subagent`，委派 0 次。

**优化方向**：
1. 增加一个「长任务」评测维度：故意构造需要读大量文件、逼近压缩阈值的任务（或临时调小窗口），验证压缩触发、摘要质量、存档可读回。
2. 增加一个「委派」评测任务：注册 `run_subagent`，对比「主 Agent 自己做」与「委派给子 Agent」的 Token 与通过率，量化委派的上下文开销。

**预期收益**：把两块「未验证」变成「已验证」，避免在长任务上盲飞；委派如果确实省钱，会改变 7.1/7.3 的优先级。

**风险**：新任务会改变套件，必须单独版本化，不能混进当前三轮基线；构造不当会变成玩具题。

**怎么验证**：新套件下单独跑 3 轮，与 checkers-v2 的数据分开归档、分开汇报，不与 57/60 合并。
