# 研发流程

> 本文规定 agent-Kernel 怎么接需求、做设计、改代码、验证和交付。它是研发流程，不是内核运行时功能，也不替代 `AGENTS.md` 和 `CODING_STANDARDS.md`。

## 1. 先判断任务类型

不同任务走不同流程，不要所有事情都套一份大方案。

| 类型 | 适用情况 | 要不要先提交方案 |
| --- | --- | --- |
| 简单修复 | 问题明确、改动范围小、不改变架构和用户可见行为 | 通常不需要，先定位再修 |
| 功能开发 | 新增能力、改变 Agent 行为、涉及多个模块或工具协议 | 需要，方案确认后再编码 |
| 架构重构 | 调整 Core、模块边界、消息协议、会话生命周期、工具执行链等 | 必须，先完整评审并得到用户确认 |
| 研究分析 | 对比源码、调查方案、评估技术选型，不要求改代码 | 不编码，先交研究结论 |

拿不准时，按风险更高的类型处理。不要为了省步骤，把架构改动说成普通 Bug 修复。

## 2. 所有任务都先做的事

1. 读根目录 `AGENTS.md`；准备修改 `src/` 或 `test/` 时，先读 `CODING_STANDARDS.md`。
2. 阅读与本次改动有关的 `docs/architecture.md`、设计文档、行为契约和 ADR。不要把所有文档一次性塞进上下文，只读相关部分。
3. 检查当前代码、测试和 Git 历史，确认现在到底怎么运行。代码是当前行为的主要依据，旧课程和研究资料不能证明功能已经实现。
4. 把结论分清楚：**事实**要有源码、测试或运行结果依据；**推断**要标明是推断；**未知**不能编成事实。
5. 开始修改前确认工作区状态。先看 `git status --short --branch` 和当前分支，不覆盖、不清理其他会话留下的修改。

## 3. 简单修复流程

适用于能明确复现、影响范围有限的 Bug 和小维护。

1. 复现问题，找到真正负责的模块和已有测试缝。
2. 说明问题原因、准备改哪些地方，以及明确不改哪些地方。
3. 先补回归测试，再做最小修改；如果现有测试已经准确覆盖问题，不重复造测试。
4. 运行相关测试，再运行 `npm run check` 和 `npm run eval:check`（涉及代码时）。
5. 检查完整 diff、相邻功能和文档影响。
6. 汇报原因、修改、验证结果，以及没有验证的部分。

如果排查后发现问题实际涉及架构、协议或用户可见行为，停止按简单修复推进，转到功能开发或架构重构流程。

## 4. 功能开发流程

适用于新增能力、改变 Agent 行为、扩展工具或跨模块修改。

1. **研究现状**：先读相关源码、测试、ADR 和成熟项目的实现依据，确认当前缺口。
2. **写 Spec**：复制 [Spec 模板](./agents/spec-template.md)，放到 `.scratch/<feature-slug>/spec.md`。
3. **讲清方案**：写明目标、当前问题、做与不做的范围、实现方案、备选方案、模块影响、兼容性、验收标准、测试、风险和回滚方式。
4. **拆分任务**：把可独立完成的工作拆到 `.scratch/<feature-slug>/issues/`，每个任务一个文件，并标明依赖关系。
5. **等待确认**：把完整方案交给用户。用户确认方案后，才开始实现；没有确认，不提前写功能代码。
6. **分步实施**：按已确认的范围开发。遇到需要扩大范围、改变方案或新增副作用时，先说明并重新确认。
7. **验证和审查**：按第 6、7 节完成测试、真实任务验证和独立 Review。
8. **交付**：更新受影响的文档，创建 PR，按 PR 模板说明修改和验证情况。

## 5. 架构重构流程

架构重构风险最高，不能边想边大改。

1. 先画出现有执行链、模块依赖和关键数据流，引用具体文件与测试。
2. 明确现有问题：哪些是已证实的问题，哪些只是可能的改进。
3. 至少比较当前方案与一个可行替代方案，说明性能、复杂度、Token、兼容性和维护成本。
4. 写清本次目标、非目标、模块边界、迁移步骤、验收标准、失败处理和回滚方式。
5. 对关键不变量设计测试；需要长期遵守的架构取舍再记录 ADR，不为普通实现细节滥加 ADR。
6. 提交完整方案，等待用户明确确认。
7. 确认后按小步骤重构；每一步都保持可检查、可测试，不把无关功能混进来。
8. 由未参与实现的人或独立 Agent 检查完整 diff；修复后重新运行验证。
9. 只有测试、评审和交付说明都完整，才进入合并。

## 6. 测试与真实验证

不同检查证明的事情不一样，不能用一个“测试通过”代替全部验证。

| 检查 | 能证明什么 | 什么时候跑 |
| --- | --- | --- |
| 相关单元 / 集成测试 | 本次涉及的行为符合预期 | 每次代码修改 |
| `npm run check` | TypeScript 检查和全部确定性测试通过 | 代码修改完成后 |
| `npm run eval:check` | 评测任务初始状态有效，检查器没有明显失效 | 修改评测或 Agent 能力后；常规代码交付也应执行 |
| `npm run eval` | 真实模型完成任务的情况、请求数、工具调用、Token 和耗时 | 提示词、工具说明、模型交互或 Agent 能力发生变化时，按需执行 |
| GitHub Actions | Linux、Windows、macOS 上的自动化检查 | PR 自动执行 |
| 人工 / 真实环境验证 | 真实终端、交互和模型行为是否符合预期 | 变更影响真实交互或单测无法覆盖时 |

注意：

- `npm run eval` 会真实调用模型并产生费用；没有执行就不能声称评测通过。
- 真实评测有波动，比较时尽量使用同一任务集、同一模型配置和相近环境。
- 如果环境不支持某项验证，要明确写出没测什么、剩余风险是什么。
- 旧评测基线不能和新任务集混在一起比较；修改检查器时要说明评测版本变化。

## 7. 独立 Review

开发者检查自己的代码容易漏掉设计时的假设。重要功能和重构应安排独立 Review。

Reviewer 只检查，不顺手改代码；重点检查：

- 是否满足需求和验收标准，有没有做多或漏做。
- 是否破坏模块依赖、消息配对、生命周期、预算、取消和错误处理等不变量。
- 是否引入安全、数据丢失、资源泄漏、Token 成本或兼容性问题。
- 测试是否验证外部行为，是否存在“测试通过但检查器没测到”的情况。
- 文档、ADR、配置和实际代码是否一致。

问题按影响区分：

- **阻塞**：可能造成数据损坏、错误执行、核心功能不可用或严重安全问题；修复前不合并。
- **重要**：明显行为错误、关键边界缺测试或方案与需求不符；原则上修复后再合并。
- **一般**：可维护性、说明或非关键优化；记录后决定是否本次处理。

修复 Review 问题后，必须重新检查对应测试和最终 diff。不能只回复“已修复”而不验证。

## 8. 分支、并行开发和 Git 操作

- 一个独立任务使用一个分支；需要并行开发时，优先使用独立 Git Worktree。
- 仓库提供 Worktree 管理命令：`npm run worktree -- create <branch> [base]` 创建，`npm run worktree -- list` 查看，`npm run worktree -- remove <branch>` 删除干净的工作区。新工作区放在**执行命令的当前 Worktree** 的 `.worktrees/` 目录中；默认从当前 Worktree 的 HEAD 创建。删除不会删分支；有未提交、未跟踪、被忽略文件或特殊索引标记时拒绝删除。
- 多个 Agent 或开发会话不能同时修改同一个工作目录。共享只读资料可以，共享写入目录不可以。
- 开始前检查工作区状态；发现其他会话的未提交修改时，先保护现场，不覆盖、不清理、不擅自暂存或提交。
- 不用强制推送、重置、清理或变基来“解决”不清楚的状态。出现冲突先查明归属，再制定方案。
- 项目当前采用 Full Access：运行时没有内置权限审批层。但这**不等于**自动获得 Git 历史操作授权。
- commit、push、merge、rebase、reset、clean、stash 等会改变仓库状态的操作，必须由当前任务明确授权具体动作。用户只授权写代码，不代表同时授权合并。

## 9. 文档与交付

按文档职责更新，不要把同一份内容复制到多个地方：

| 内容 | 放在哪里 |
| --- | --- |
| 项目介绍和用户用法 | `README.md` |
| AI / 开发者必须遵守的简短规则和代码导航 | `AGENTS.md` |
| 代码写法与测试规范 | `CODING_STANDARDS.md` |
| 当前真实架构 | `docs/architecture.md` |
| 稳定的跨模块设计原则 | `docs/design/` |
| 长期行为约束 | `docs/contracts/` |
| 难反转、有取舍的架构决定 | `docs/adr/` |
| 研发流程 | 本文件 |
| 功能设计与验收标准 | `.scratch/<feature-slug>/spec.md` |
| 临时任务拆分和进度 | `.scratch/<feature-slug>/issues/` |
| Agent 真实表现 | `eval/` |

PR 描述使用 [Pull Request 模板](../.github/PULL_REQUEST_TEMPLATE.md)。交付时至少说明：改了什么、为什么改、影响范围、跑了哪些检查、哪些没有跑、Review 结果、剩余风险和回滚方式。

**最终原则：先理解现状，再确认方案；先小步实现，再用测试和真实任务证明；最后独立审查并清楚交付。**
