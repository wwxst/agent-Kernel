# Agent-Kernel 整体评测体系

## 目标

评测体系回答三个问题：

1. Agent 能不能把真实开发任务做完？
2. 完成任务花了多少模型请求、Token、时间和费用？
3. 改动前后，任务成功率和代码质量到底有没有变好？

评测是内核的证据层，不替代单元测试、类型检查、安全审查，也不根据单次分数自动决定架构方向。

当前评测套件版本：`2026-11-27-eval-system-v6`。04-create-doc 检查器允许两列「命令 + 说明」或三列「npm script + 命令 + 说明」，但仍核实每个 npm script 和实际命令。22-multi-tool-refactor 检查器比较测试文件前统一换行符，接受语义等价的新增测试标题，但仍要求原始测试逐字保留。

## P1：评测数据采集

入口：`eval/run.mjs`、`eval/diagnostics.mjs`。

每轮评测记录：

- 任务成功/失败、失败分类、任务耗时和整轮墙钟耗时；
- 业务模型请求、上下文摘要请求、工具调用次数；Token 合计包含摘要请求，两类请求分开计数；
- 输入、输出、总 Token，以及明确报告的缓存命中 Token；
- 缺少 usage 或缓存用量时的未知计数，不把未知补成 0；
- 上下文消息规模、System Prompt 字符数、工具定义规模；
- 工具执行耗时、结果长度、工具错误、文件变化和快照覆盖情况；
- 上下文压缩次数、摘要请求数、压缩失败和观察器错误；
- Commit、分支、工作区是否干净、模型、端点主机/路径、Node、OS、架构、并发；
- 系统提示词、工具定义、运行时代码、评测执行器、任务集和价格表的 SHA-256 指纹。

正常评测不必开启详细追踪；需要定位问题时使用 `--trace`。追踪会增加 I/O，带追踪的耗时不能直接和无追踪结果混比。

结果默认写入 `eval/results/`，该目录不进入 Git。可通过 `EVAL_OUTPUT_FILE` 指定结果文件，供 A/B 实验分别保存。

## P2：费用估算与代码质量盲审

### Token 与费用

入口：`eval/cost.mjs`、`eval/pricing.example.json`。

- 费用只按用户自己填写的价格表计算，不内置、猜测或自动更新模型价格。
- 价格按每百万输入、缓存输入和输出 Token 配置。
- 没有价格配置时，金额为未知。
- 请求 usage 缺失时，只能报告已知请求的小计，并标记不完整。
- 缓存价格与普通输入价格不同、但缓存命中量未知时，不给出费用金额。
- 费用字段使用价格表声明的币种，不把人民币等其他币种误标成美元。

价格表示例中的费率是占位字符串，必须替换成真实数字后才能使用。

### 代码质量盲审

入口：`eval/quality-review.mjs`。

盲审不是让评审者先看模型名或提交记录，而是把同一任务的两份最终工作区随机改名为 `candidate-1` 和 `candidate-2`，并提供共同的任务说明和初始文件。

盲审包包含：

- 任务要求；
- 共同初始工作区；
- 两份匿名候选最终文件；
- 评分规范、JSON 评分卡模板和结构 Schema。

候选与 Commit、分支、模型的对应关系单独保存在 `*.answer-key.json`，不能发给审查者。生成盲审包前会核对两轮评测配置、任务提示和初始夹具；不一致时拒绝生成。盲审包会对任务说明、初始夹具和两个候选文件都检查常见密钥与高置信度凭据，避免把本机密钥交给审查者。

评分维度（每项 0～4 分）：

1. 正确性；
2. 完整度；
3. 稳定性与安全；
4. 可维护性；
5. 修改范围。

执行规则：

- 同一任务的两份候选由同一组至少两名不同审查者独立评分；
- 每个维度必须写具体证据；
- 同一候选重复使用同一个 reviewerId 会被拒绝；
- 任一维度相差 2 分及以上、推荐结论不同、存在阻断问题、审查者不足或候选缺失时，标记需要补审/第三方裁决；
- 数据汇总不会替第三名审查者做决定，也不会用平均分抵消阻断问题。

评分标准：`eval/quality-review/rubric.md`。
评分结构：`eval/quality-review/scorecard.schema.json`。

## P3：A/B 对照实验

入口：`eval/ab.mjs`、`eval/compare.mjs`。

使用者准备 A（基线）和 B（候选）两个独立代码目录。实验运行器：

- 默认执行 3 轮，默认并发 1；
- 每轮交替 A/B 的执行顺序，减少固定先后顺序造成的时间偏差；
- 使用同一进程环境中的模型、端点和价格配置；
- 显式声明本轮唯一实验因素：`agent-runtime`、`system-prompt` 或 `tool-definitions`；
- 对比前必须确认两边使用完全相同的评测执行器指纹；系统提示词实验还要求除提示词文件外的运行时代码指纹相同；
- 自动核对提示词和工具定义指纹：测试提示词时工具定义必须不变，测试工具定义时提示词必须不变，测试运行时逻辑时两者都必须不变；
- 每轮分别保存 A、B 原始 JSON 结果；
- 自动检查模型、端点、实验 ID 与 A/B 标签、任务集指纹、价格表指纹、运行环境、并发、任务集合和任务预算；
- 配置不一致或存在基础设施错误时，将该轮标记为无效；
- 对有效轮次计算成功率、请求数、摘要请求、工具调用、输入/输出/总 Token、缓存 Token、耗时和费用差值；
- 输出逐任务回归/提升表、逐轮有效性和多轮中位数报告；至少 3 轮全部有效且每轮 A/B 都具有互不重复的运行 ID 才标记为可用于决策，否则明确标记为探索性结果。重复放入同一次运行不能冒充三轮独立证据。

A/B 工具只运行已经准备好的目录，不会创建或删除 Git 分支，不会切换 Worktree，也不会修改 main。若工作区不干净或 Git 状态未知，会在报告中明确警告；usage 缺失时不把 Token 下限当成精确差值。

## P4：复杂任务与内核专项场景

真实模型任务集当前共 22 个任务。

新增任务：

- `21-long-context-compaction`：在固定的上下文窗口和 Token 预算下验证长上下文聚合能力——逐一读取 16 份迁移记录，整理成按日期精确排序的表格；接受不同 Markdown 空格与对齐写法，但日期顺序和 16 条记录的原始字段必须完全一致。压缩正确性由离线 `context-compaction` 场景和单元测试覆盖，本任务不再强制触发压缩。
- `22-multi-tool-refactor`：跨文件修复格式化逻辑，保留原测试、补齐边界测试，并实际运行测试命令；检查器会核实 Agent 的 read、write/edit、shell 工具成功完成，且 Node 测试命令的 shell 实际返回退出码 0。仅发起工具调用或非零退出不能作为成功证据。

离线专项场景使用假模型和真实 Agent / ToolRegistry，不调用外部 API：

- `context-compaction`：验证长对话触发压缩，摘要提交后任务仍能完成；
- `serial-tool-batch`：验证同一批工具调用严格串行执行；
- `tool-error-feedback`：验证工具错误状态返回模型后，Agent 能继续处理。

真实模型压缩专项评测（`eval/compaction.mjs`，`npm run eval:compaction`）只把摘要请求发给真实模型：业务回合由脚本化 ChatClient 回放。单次与连续压缩使用 32768 token 窗口、2048 token 输出预留；超长纠正与持续超长使用 8192 / 1024（对齐 v5 真实场景）。超长故障由脚本合成固定 1.5 倍硬上限的合法摘要，纠正重试才调用真实模型，持续超长完全不调用端点。它验证单次压缩、同一 Run 连续压缩、超长摘要纠正重试，以及持续超长时的有界失败、不提交和原历史不变。它按 `EVAL_BUDGET_TOKENS`（默认 200000）统计付费摘要 token，超限即中止剩余场景；不改变 v6 任务集。

这些离线场景验证内核行为，不代表真实模型在所有任务上的成功率。

## 模块关系

```text
真实任务集 ──> eval/run.mjs ──> 原始评测 JSON
                     │
                     ├── eval/diagnostics.mjs 详细请求与工具追踪
                     ├── eval/cost.mjs        Token 费用估算
                     └── eval/summary.mjs     同口径多轮汇总

A/B 两个代码目录 ──> eval/ab.mjs ──> eval/compare.mjs ──> 对照报告

A/B 原始结果 + --keep 工作区
          └──> eval/quality-review.mjs ──> 匿名盲审包
                                           └──> 独立评分卡汇总
```

## 验收方式

不需要 API Key、不会产生模型费用的检查：

```bash
npm run check
npm run architecture:check
npm run eval:check
npm run eval:scenarios
```

真实模型评测：

```bash
npm run eval
npm run eval:summary
```

A/B 对照：

```bash
npm run eval:ab -- --a-dir ../agent-kernel-A --b-dir ../agent-kernel-B --factor system-prompt --rounds 3 --jobs 1 --keep
```

CI 在 Linux、Windows、macOS 上运行类型检查、单元测试、架构边界检查和评测集自检；不会在 CI 中调用真实模型。

## 当前结论与边界

- P1～P4 的评测工具、任务和规范已落地。
- 离线测试和 CI 可以证明评测工具自身按预期工作。
- CI 通过不等于 Agent 的真实模型任务通过。
- 当前套件 v6 已有三轮真实模型基线（提交 `dfcaf8a`、`hy3`、22 个任务、并发 4）：63/66 通过（95.5%），逐轮 20/22、22/22、21/22；中位数 147 次请求 / 652,130 tokens / 112.6 秒。`04-create-doc` 只有 1/3（表格格式契约），`08-extract-duplication` 2/3，其余 20 个任务 3/3。
- 该基线没有触发上下文压缩：`summaryRequests` 与 `compactions` 均为 0，32768 的上下文窗口只配在 `21-long-context-compaction` 上；压缩由离线专项场景 `context-compaction` 覆盖，不是这三轮的证据。记录里没有价格表（`pricing.configured: false`），费用未知，不能由 Token 直接换算。
- 历史旧套件的分数不能直接当成新套件成绩：checkers-v2 的 57/60（20 题、`76a024a`）和 v1/v2 的六轮数字都使用不同的任务口径与提交。
