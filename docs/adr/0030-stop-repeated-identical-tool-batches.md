# ADR-0030：连续重复的工具批次视为无进展，停止而不是继续烧预算

## 决定

- 判定单位是**一整批工具调用**，不是单个调用。签名只取「工具名 + 规范化后的参数」，**保持调用顺序**：同一批里调换两个调用的先后是不同行为，不能算相同。
- 参数在比较前做规范化：对象键递归排序，数组顺序原样保留。模型每次生成的键顺序可能不同，那只是措辞差异。参数不是合法 JSON 时保留原文，让它仍然形成一个稳定签名，最后由 `ToolRegistry` 报参数错误。
- 结果也参与判定：只有**调用与结果都相同**才算「无进展」。结果一变，计数重新从 1 开始。
- 连续 `MAX_IDENTICAL_TOOL_BATCHES = 3` 批相同，就**不执行第 4 批**：给被跳过的调用补上 `not run` 结果，保持 assistant / tool 配对完整，然后以明确的错误结束本次 Run。
- 只有**整批都正常执行完**才记录。进程树清理未确认、取消打断、部分调用被跳过时，这一批不参与判定 —— 不完整的批次不能证明「模型在原地打转」。
- 计数**按 Run 重算**：上个任务里重复过，不该让这个任务少一次机会。
- 判定放在预算检查与「最后一步」检查**之后**。预算已经耗尽时，报预算错误比报无进展更准确。

## 为什么这样做

模型陷入循环的典型形态是：同一个工具、同样的参数、拿到同样的输出，然后再来一次。它每次都能拿到一个「成功」的结果，所以它不会自己意识到在打转。

- **`maxSteps` 抓不住根因**：步数上限确实能终止循环，但它是通用刹车 —— 报错说「步数用完了」，用户看不出是任务太大还是模型卡住了。同一件事需要两种解释时，说明判定标准混在了一起。
- **只比调用会被轮询工具误伤**：`shell` 里跑 `tail`、查后台任务状态、等文件出现，都是「同一个调用、结果会变」。所以结果必须进签名。
- **只比结果会误判**：不同工具碰巧返回同一段文本（比如两个都会失败的 `grep`）不代表没进展。
- **不能按 `tool_call_id` 判重**：id 每次响应都不同，用它做键等于永不重复。
- **不交给模型自查**：它看不到自己历史里的重复，也没有理由怀疑自己。这类保护只能由内核提供。
- **不做成可配阈值**：当前没有证据表明 3 不对。多一个环境变量就多一个「配错了才出事」的地方，等真实任务跑出反例再说。

## 代价与边界

- **合法的重复调用也会被中断**。一个轮询工具如果连续三次返回**完全相同**的状态文本（「仍在运行」），会被判定为无进展。这是这个决定最主要的误伤面：它要求轮询工具的输出里带上能反映变化的字段（时间戳、进度、计数），否则三次不变就是三次不变。
- **3 是硬编码常量**。要调只能改代码、重跑测试，不能靠配置绕过。
- **一次 Run 只省下「之后所有」的请求**：停止发生在第 4 批之前，前三批的成本已经花掉。它的价值在于不再继续，而不是提前预知。
- **错误文案进 Transcript**，模型会看到「identical tool batches / no progress」。这既是给用户看的，也是给模型看的：它可能在下一个 Run 换策略。但内核不保证它会。
- **不覆盖语义层面的重复**：换一个工具名做同一件事、把参数改一个无关字符，都能绕过判定。这是有意的 —— 那种判定需要理解任务，不属于内核。

## 不变量

- 停止之前先补齐配对：被跳过的调用一定有对应的 `not run` 结果，assistant / tool 的 id 配对不因停止而断裂。
- 计数只在「签名相同且结果相同」时递增，否则重置为 1；不存在只凭其中一半就递增的路径。
- 计数不跨 Run 继承，`beginRun()` 清空。
- 批次不完整（进程树清理未确认、取消、部分调用跳过）时不记录，也不递增。
- 判定不改变协议、不改变工具层、不改变 `ToolRegistry`：模型看到的工具与参数校验与之前完全一致。
- 预算与「最后一步」的检查优先于无进展判定。
- 对应行为由 `test/agent.test.mjs` 的无进展检测用例保护：连续重复后停止且配对完整、结果变化时继续轮询、参数键顺序不影响判定、计数按 Run 重算。
