# 只保留完全访问（Full Access）

## 决定

agent-Kernel 只有一种运行模式：**完全访问**。删除了 `read-only` / `workspace-write` / `full-access` 三档策略、Shell 逐次审批、权限规则文件、审批菜单、`--permission`、`AGENT_PERMISSION`、`/permission` 和 `Shift+Tab`。

- `ToolRegistry.execute()` 只剩三步：校验参数 → 执行工具 → 返回结果。普通失败折成 `ERROR` 文本；进程树清理未确认仍抛 `ProcessCleanupError`。
- 文件工具不再有工作区边界：相对路径以 `WORKDIR` 为基准，绝对路径直接使用，`../` 可以走出默认目录；符号链接解析到实际目标。
- `shell` 直接执行，默认 cwd 是 `WORKDIR`，命令内可以 `cd` 到任意位置；保留超时、输出上限、取消信号、进程树清理与跨平台兼容。
- 没有 agent-Kernel 自己施加的网络限制；能否出网由操作系统、代理与防火墙决定。
- 系统提示词明确告诉模型：当前是完全访问，没有工作区目录边界，普通操作不需要请求授权。

## 为什么

旧设计的三档模式**看起来在限制，实际不是沙箱**：`shell` 一旦放行就和启动者同权，路径守卫只防模型手滑、不防恶意代码（[ADR-0008](./0008-trusted-local-agent.md)）。代价却是持续打断开发者：每跑一条命令都要确认，为了少被打断又得维护三层规则文件与「以后不再问」菜单。一套没有隔离效果、却需要用户持续投入的机制，比没有更危险——它让人误以为风险已经被管住。

实际使用里，开发者真正想要的是「让它自己干活」。所以把选择收敛成一个：默认按开发者的真实权限工作，把隔离需求交给容器、虚拟机、独立用户或只读挂载这些真正的边界。

同时修掉了一个不一致：旧版本里 `shell` 能访问整个磁盘，内置文件工具却被 `Workspace` 挡在工作区内。现在两者能力一致，模型不需要猜「这个路径该用哪个工具」。

## 代价与边界

- **完全访问不是提权。** 进程仍以启动它的操作系统账户运行，没有 `sudo`、没有管理员权限提升，也不绕过系统安全机制。
- 没有审批，就没有「停下来再看一眼」的机会。误删、误改、误跑命令的后果由开发者自己承担；重要仓库建议在容器、虚拟机或独立用户里运行。
- 删除审批模块不等于删除稳定性保护：超时、输出上限、取消、子进程清理、原子写入、有界读取、扫描预算、正则超时都保留。
- 删除权限规则文件后，`permissions.json` / `permissions.local.json` 不再被读取。残留文件不会报错，但也不再有任何作用；启动时传入已移除的 `--permission` 或 `AGENT_PERMISSION` 会明确报错，避免「以为还在限制」。
- 历史决策 [ADR-0013](./0013-permission-is-a-policy-not-a-sandbox.md) 与 [ADR-0018](./0018-project-permission-rules.md) 保留，但已标注为被本决定取代。

## 不变量

- 只有一种模式，任何启动入口（CLI、TUI、评测、测试装配）都默认完全访问。
- 文件工具与 `shell` 的访问能力一致，都以当前操作系统账户为准。
- 工具失败仍折成非空 `ERROR` 文本，不抛异常、不终止 Run。
- 取消、超时、进程树清理、输出上限继续生效，不因删除审批而削弱。
- 系统提示词与实际能力保持一致：代码允许的，模型也被明确告知可以做。
