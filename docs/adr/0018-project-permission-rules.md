# ADR-0018：权限规则按参数数组匹配、分三层、拆不动的命令一律要问

**状态**：已实现（2026-11-11）

## 背景

`Permission` 只有三档整体模式。`workspace-write` 下每条 shell 都要人工确认——排查一个 bug
跑十几条命令，就是十几次打断。Claude Code 和 Codex 都有「这条命令以后别再问」的机制，
我们需要一个，但直接照抄会引入两个已知问题：匹配方式会漏，存储位置会污染团队配置。

## 决定

### 1. 分三层，跟着人走和跟着项目走分开

| 层 | 文件 | 进 git？ |
| --- | --- | --- |
| 本地 | `.agent-kernel/permissions.local.json` | ❌ 自动写进 `.gitignore` |
| 项目 | `.agent-kernel/permissions.json` | ✅ |
| 用户 | `~/.agent-kernel/permissions.json` | — |

起因是一个真实缺陷：菜单里点「以后不再问」如果写进项目层，你个人图省事放行的一条命令
会让整个团队继承，`git status` 里还多一行改动。**一次点头属于个人偏好，不属于团队约定。**

Claude Code 的 user / project / local 三层是参照对象，它连 gitignore 都替用户配好。

### 2. 匹配参数数组，不匹配字符串

Claude Code 的 `Bash(ls *)` 是字符串前缀匹配，所以 `ls && rm -rf /` 也以 `ls ` 开头，照样命中。
它靠别的层兜底：六种权限模式、`auto` 模式的分类器、沙箱。**这三样我们都没有**，所以不能照抄。

规则写成 `shell:git status`，解析成 `{ tool: "shell", argv: ["git","status"] }`，
逐项等于命令开头才算命中。`git statuses` 不命中，`git status && rm -rf /` 也不会因为
第一段命中就整条放行。

### 3. 复合命令：整条精确匹配，不拆成前缀

`cd demo && node server.js` 这种命令，按前缀记只能记第一段 `cd demo`，第二段就没人管了——
`cd demo && rm -rf /` 会被一起放行。

所以规则分两种：**单段是前缀规则，多段是精确规则**。写几条就是几条：

```json
{ "allow": ["shell:cd demo && node server.js"] }
```

只匹配一模一样的那条命令。代价是**参数一变就要重新批准**（`--port 3000` 会重新问），
换来的是没有任何放宽。菜单里点「以后不再问」对复合命令记的就是这一种。

Claude Code 的 `Bash(...)` 是字符串前缀，所以它会把 `cd demo && node server.js && rm -rf /`
一起放行——同一个洞，它靠沙箱和分类器兜着，我们没有。

### 4. 复合命令拆开逐条判，取最严

`&&` `||` `;` `|` 会切开，每段单独裁决，只要有一段没被放行，整体就要问。
Codex 的 `execpolicy` 是同一思路（它用 tree-sitter，我们用保守的手写切分器）。

### 5. 拆不动就不拆

命令里出现 `$`、反引号、`>`、`<`、`*`、`?`、反斜杠、换行，或者引号没闭合、出现单个 `&`
（后台执行）时，整条命令当作**不透明**：永远匹配不上 `allow`，只能问。

**但切不开不等于不能记住**：这类命令按整条原文存成精确规则，逐字比较。
前缀规则永远不会命中它们，所以「拆不开」只影响「能不能用前缀放宽」，
不影响「能不能免问」——这一点是后来才想明白的，第一版直接不给记，
结果实战里几乎所有命令（带 `2>&1`、`$?`、通配）都拿不到那个选项。

这是有意的取舍——**手写切分器无法保证解析结果和 shell 的实际行为一致，猜错一次就是误放**。
Codex 在同样情况下也退化成「整条当作一条命令评估」。

### 6. 裁决：deny 跨层最强，其余按层序

`deny` 一旦出现在任何一层就拒绝，本地层的 `allow` 压不住它——团队写「不许 `rm -rf`」，
就该是团队说了算。这是安全方向上有意的不一致：**禁止比允许更有分量**。

其余情况按层序 `本地 → 项目 → 用户`，第一个命中的层给结论；同一层内 `deny → ask → allow`。

### 7. 规则只在 workspace-write 生效

`full-access` 的语义就是全部直接执行，`read-only` 连 shell 都不给，两边都不该被一份
项目配置改写。这条和 Claude Code 的 `bypassPermissions` 跳过一切检查是同一取向。

### 8. 任何一层文件写坏了都直接报错

启动时抛出，带文件名和具体条目。静默忽略一份安全配置，比没有它更危险：
用户以为写了 `deny`，实际什么都没拦。

### 9. 信任级别本身也要能持久化

规则能跨项目（用户层），但「整个模式」之前只能靠 `--permission`，换个目录就等于回到
`workspace-write`。这暴露了一个不对称：**「我信任这台机器」是一个长期判断，却只能用一次性的
命令行参数表达**。

所以 `.env` 支持 `AGENT_PERMISSION`，优先级 `--permission` > `AGENT_PERMISSION` > 默认。
命令行必须压过配置文件，否则一次临时提权会被文件顶回去。

写错值直接报错，理由同第 8 条：退回默认值会让用户以为配置生效了。

Codex 把 `approval_policy` 放进 `~/.codex/config.toml`，解决的是同一个问题。

## 代价

- 带通配符、命令替换、重定向的命令**只能用精确规则**，改一个字符就重新问。
- 复合命令同理：整条精确记住，参数一变就要重新批准。
- 三层意味着三个文件都可能出错，报错信息必须指明是哪一层、哪一条。
- 项目层进版本库，团队共享一份规则意味着共享一份信任决策——这需要在 PR 里被 review。
- 多了一个配置入口（`.env` 的 `AGENT_PERMISSION`），排查「为什么它不问/为什么它在问」时要多看一处。

## 不变量

1. `deny` 不能被更低优先级的层推翻。
2. 规则**不能**让 `deny` 之外的东西绕过模式：`read-only` 下 allow 规则不生效。
3. 一段命令没被任何规则放行，整体就不放行。
4. 解析不确定的输入，结论只能是「问」。
5. 「记住」记住的是**这一条命令**，写进**本地层**，不是「这个工具」也不是「我点过头」。
