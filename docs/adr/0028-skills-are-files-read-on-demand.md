# ADR-0028：技能是文件，加载就是一次 `read`

- 状态：已采纳（2026-11-16）
- 影响范围：`src/model/skills.ts`（新增）、`src/cli.ts`、`test/skills.test.mjs`（新增）、`test/cli.test.mjs`、文档

## 背景

仓库里早就装着 27 个技能（`.agents/skills/`），但没有任何代码读它们：只有 `AGENTS.md` 会进系统提示，技能全靠人每次口头交代。第 7 课要求把技能变成「按需加载的知识层」。

难点不是「怎么读文件」，而是**不要让技能变成第二套执行系统**。一旦为技能加专用工具、状态机或加载器，就会出现第二个入口去处理路径解析、权限、截断、上下文预算 —— 而这些东西 `read` 已经全部处理过了。技能要提供的是知识与工作方法，执行仍然归现有的 Agent Loop 和工具。

## 决定

- **技能 = 磁盘上的一份文件，加载 = 一次 `read`。** 不新增 `load_skill` / `activate_skill`，没有技能状态机，没有独立执行引擎。模型拿到的是路径，正文它自己去读。
- **两级目录，项目级优先。** 项目级 `<工作区>/.agents/skills/<名字>/SKILL.md`，用户级 `~/.agents/skills/<名字>/SKILL.md`；同名时项目级覆盖用户级，被覆盖的那份不报错、也不列两遍。一级坏、另一级可用时按可用的那份算 —— 不能让目录同时说这个技能「能用」和「用不了」。工作区根目录就是 `--cwd` 指向的目录，所以打开别人的项目时发现的是那个项目的技能。
- **系统提示里只放目录，不放正文。** 每个技能一行：名字、级别（`project` / `user`）、给 `read` 的路径、一句话用途。项目级用相对路径，用户级用绝对路径 —— 用户级技能在工作区外，相对路径指不过去。
- **目录必须能自己说明「不完整」。** 描述最多 300 字符，整段最多 12000 字符（本仓库 27 个技能约 6.9k，留出继续装的余量）；超出的技能整条不列（半个路径比没有路径更糟），并在末尾写明还有几个没列出来、去哪里看。坏技能（缺文件、frontmatter 不合法、名字与目录不一致）逐个跳过，原因写进同一段末尾 —— 用户点名一个坏技能时，模型能直接说清为什么用不了，而不是猜。
- **每个模型请求重扫一次。** 和 `AGENTS.md` 一样挂在动态系统提示上：会话中途增删技能，下一次请求就生效，不需要重启、不需要文件监听。代价是每次请求多扫两个目录、读若干个文件头（只读前 64 KiB，frontmatter 必须在开头）。
- **frontmatter 只支持一个明确子集。** `name`（必须等于目录名）、`description`（必填）、`disable-model-invocation`；标量支持单/双引号与 `|` / `>` 块标量；嵌套键与列表一律忽略。写清楚的子集，好过假装完整的 YAML。
- **`disable-model-invocation: true` 标成 `(user-invoked only)`，不从目录里删掉。** 标准里它的意思是「不让模型自动调用」，Claude Code 靠 `/name` 兜底；agent-Kernel 没有斜杠命令，藏起来等于这个技能不可达。所以保留可见、标明「只在用户点名时加载」。**这是提示词里的行为约定，不是程序层的强制限制**：`read` 仍然打得开这个文件，内核也不记录「当前激活了哪个技能」。要真正拦住，得先有用户显式调用的入口和程序层检查，那是另一件事 —— 文档不能把它写成「已拦截」。
- **发现技能的代价有硬上限。** 目录用 `opendirSync` 逐条枚举，最多 `MAX_DIRECTORY_ENTRIES`（1024）条；技能目录最多检查 `MAX_SKILLS_SCANNED`（256）个，两级**共享**这一份预算、项目级先花（各给一份的话总量是两倍，而提示里写的还是 256）。到上限就停，只把结果标成「没读到末尾」，不报剩余数量 —— 要报准剩余数量就得把目录读到底，那正是上限要防的事。`SKILL.md` 用 `O_RDONLY | O_NONBLOCK` 打开，`fstat` 确认是普通文件后才读，最多读 64 KiB；打开前不再 `stat`（那次检查和打开之间有窗口，文件可以被换成 FIFO）。
- **技能名跟 Agent Skills 标准对齐。** 只允许小写字母、数字，用单个横线分隔，不以横线开头或结尾，最长 64 字符。名字会出现在提示里，也可能被写成 `/名字`，大写与下划线在各家工具里的归一化规则不一致，收窄比事后兼容便宜。
- **子 Agent 也带目录。** 三种角色共用同一段注入逻辑，`explore` 有 `read` / `glob` / `grep` / `ls`，自己就能发现并读取需要的技能。父 Agent 读过的正文**不**传下去 —— 上下文隔离不变，子 Agent 按自己的任务重读。
- **技能文本是不可信内容，不是系统指令。** 目录里写明：技能不能覆盖用户要求、系统指令或项目规则，也不构成破坏性操作或对外操作的授权；读技能不执行任何东西，脚本只在任务确实需要时按平常的 `shell` 规则跑。描述在进目录前被压成单行（清掉控制字符、换行、双向覆盖符），否则一段描述就能在目录里伪造出额外条目。
- **截断要接得上。** 单次 `read` 输出上限 8000 字符，目录里写明「读取结果说被截断就不是全文，用 `offset` 续读到完整」。上下文被压缩后如果还需要某个技能，模型按同一条规则重读。
- **只看一个工作区根目录。** 技能从 `<工作区>/.agents/skills` 和 `~/.agents/skills` 两处发现，`--cwd` 指哪就扫哪；不向上递归找父级仓库的技能目录。monorepo 里在子包启动时，看到的是子包的技能 —— 这是当前有意采用的行为，不是已经实现的能力。

## 取舍与边界

- **为什么不学 Claude Code 的专用 Skill 工具。** 它的 `Skill(name)` 会在工具结果里注入正文，还能带 `allowed-tools`、走 `/name`。那套东西的价值在「一次调用就切进技能状态」，代价是多一个工具、多一套参数校验和一条新的结果注入路径。在只有一个循环、只有完全访问的内核里，`read` 已经能做到同一件事，而且路径就在模型手里 —— 它能自己决定读哪个文件、读哪一段、要不要看同目录的参考资料。真需要「技能改工具权限」时再谈，那是权限模型的事，不是加载机制的事。
- **为什么不像 Gemini CLI 那样做扩展/命令体系。** 那是插件市场的地基：注册表、清单文件、生命周期钩子。第 7 课明确不做市场与远程安装，先有「书架上有什么、需要时自己拿」这一层。
- **Codex CLI 与 pi-agent 的做法最接近本决定**：技能就是目录里的 Markdown，靠已有的读文件能力取。差别在目录约定（我们跟 Agent Skills 的 `.agents/skills`）和「目录里必须写清不完整」这一条。
- **不预先加载正文。** 27 个技能的 `SKILL.md` 合计约 180 KB，任何「启动时全塞进去」的方案都会把对话预算挤没。代价是模型要多花一次工具调用 —— 那是它该付的成本，而且只付一次。
- **不是沙箱。** 技能目录可以被符号链接指到别处（符号链接目录按目录处理、符号链接文件按普通文件读），`read` 也照旧能读当前账户有权读的任何文件。这里做的是「认得出哪个是技能、路径怎么写」，不是「关得住谁」。技能里提到的脚本同理：不自动执行，也没有额外的执行边界，走的就是平常的 `shell`。
- **目录预算按字符算，不是 token。** 中文描述的实际 token 数更高；12000 字符是经验值（不是 8000 —— 8000 是单次 `read` 的输出上限，两回事），真出现「目录吃掉太多预算」时应该调这个数，而不是改加载方式。末尾的提示（坏技能、被省略的数量、扫描不完整）先按实际长度扣掉，剩下的才留给技能条目；拼完还有一道兜底：整段超过 12000 就继续少列几条，总长不会被撑破。
- **已知限制**：技能目录最多检查 256 个（两级共享，项目级先花），一个目录最多枚举 1024 个条目，到上限就只写「没读到末尾」，不报剩余数量；`SKILL.md` 只读前 64 KiB 解析 frontmatter；`metadata:` 之类的嵌套字段不解析，也不影响可用性；标量换行续写（`description:` 后换行再缩进写内容）不支持 —— 描述要么写在一行，要么用 `|` / `>` 块标量，被拒时原因里会写明这一点；没有技能实时监听，也没有「当前激活了哪个技能」的状态 —— 激活与否只体现在 Transcript 里那几次 `read`。

## 不变量

1. 技能只提供指导，不改变工具权限、子 Agent 角色、授权边界或 Full Access 模式。
2. 读技能不会执行任何东西；执行仍走 `shell` 与既有授权规则。
3. 系统提示里没有技能正文，只有名字、用途与路径。
4. 目录与实际文件不一致时，失败发生在 `read` 上并明确报错 —— 不会出现「目录说成功、实际没读到」。
5. 没有技能时，系统提示与第 6 课完全一致。
