# ADR-0021：工具调用日志是「显式开启的 JSONL 追加文件」

- 状态：已采纳（2026-11-13）
- 影响范围：`src/core/tool-log.ts`（新增）、`src/cli.ts`（装配）、环境变量 `AGENT_TOOL_LOG`

## 背景

[ADR-0020](./0020-tool-hooks-live-in-the-registry.md) 把 Hook 机制做出来了，但生产代码一个 Hook 都没登记。
机制有没有用，只能拿一个真实需求去试。第一个需求是：事后能查「哪次工具调用、成没成、为什么失败」——
现在这些信息只存在于屏幕上的运行记录里，滚过去就没了。

## 决定

- `createToolLogHooks(file)` 造两个后置回调（成功、失败），返回**登记项**（`ToolHooksOptions`），
  不返回现成的 `ToolHooks`：调用方要能把它和别的事件拼起来再 `new ToolHooks(...)`。
- 每执行完一次工具调用，追加一行 JSON：`ts` / `tool` / `id` / `ok` / `args` / `detail`。
  成功与失败字段完全一样，读日志时不用分情况。
- 只有设了 `AGENT_TOOL_LOG=<路径>` 才登记；不设就完全不写，行为与之前一字不差。
- 写盘用同步追加（和输入历史 `ui/prompt-history.ts` 同一套做法），父目录不存在就建。
- 写不进去**不抛**，只在第一次往 stderr 说一句，之后闭嘴。

## 为什么不是「总是写」

一个默认打开的日志文件是用户没要求过的副作用：它会在工作区或家目录里悄悄长文件，
而且没有任何开关能关掉。显式开启的代价是「用户得知道有这个变量」——写在 README 配置表和启动横幅里就够了。

## 为什么不做日志轮转、查询、结构化级别

一个只追加的 JSONL 文件已经能被 `jq`、`grep`、脚本直接读；轮转和查询是另一件事，
加进来就要回答「保留几天」「按什么切分」，而这些问题现在没有真实需求。

## 代价与不变量

- **代价**：开启后每次工具调用多一次同步 `appendFileSync`（毫秒级，远小于工具本身）；
  单行最长约 2 × 2000 字符（参数与结果各自截断）。
- **不变量**：工具结果、`ERROR:` 文案、Transcript、模型请求体都不因日志改变；日志 Hook 抛错也只记
  `ToolHooks.failureCount`。
- **已知缺口**：被前置 Hook 拦下的调用不留记录 —— 它没有执行，也就没有结果事件。
  要审计「谁想跑但被拦了」，得让前置 Hook 自己写。
- **已知边界**：日志路径不做校验，写不进去靠 stderr 那一次提醒；不检查路径是否在工作区内（全访问模式，日志本来就可以放在任何地方）。
